# Changelog

All three packages (`@trama-dev/runtime`, `@trama-dev/session`, `@trama-dev/cli`) are released together under one version.

## Unreleased

### Added

- **A program can have an agent from outside do a piece of work: `tools.agent(prompt, { agent, … })`.** Somebody else's coding agent, whole — its own loop and tools, under the user's own login for it — started for the call and spoken with by the [Agent Client Protocol](https://agentclientprotocol.com), version 1. It is the third way a program has work done, with less hold than the other two: `agent.complete` is one request to a model, and the program is the harness; `agent.instruct` and `generate` have pi's agent be it; this hands the work out, and a harness that is a program can have such a call among its tools.
  - **It is a black box, and is treated as one**: a prompt in; out, an `AgentResult` — what the agent said (`text`: all of it, with an empty line between one message of its and the next; `messages`: the same, each apart — the last is its answer), whether the turn ended as one does (`ok`, `stopReason`), the conversation's id (`session`), what it said it used (`usage`), the tool calls it reported, what it said of itself (`agent`: name, version, the models it offers and the one serving, whether it goes on with a conversation and takes a system prompt), and how what was asked was in fact given (`given`).
  - **It resolves as `tools.shell` does, also where the call did not go through**: then `failure` says what stood in the way, sorted — `not-installed`, `not-logged-in`, `timed-out`, `refused`, `failed` — with the agent's own words. It throws only for a call written wrongly (found before anything is started) and in a run that was stopped.
  - **An agent is named in the configuration** — `"agents": { "claude": { "command": "npx", "args": ["-y", "…"], "env": {…} } }` in `config.json` — or by what starts it, in the call. The runtime names none, and ships no list of them.
  - **Little is held, and all of it is said.** Every permission the agent asks is granted for the once (`allow_once`) — never for always, so nothing is written into the user's settings for that agent; where it cannot be granted for the once it is refused for the once; both are counted in `given.permissions`. `system` goes as the session's where the agent says it takes one, and at the head of the prompt where it does not (`given.system`). `model` is for an agent that has none of its own: the agent's own serves otherwise, and `given.model` says whether the one named was set. `session` goes on with an earlier call's conversation, by `session/resume` or `session/load`, whichever the agent has (`given.resumed`). The client offers the agent nothing of its own — no file system, no terminal: the agent reads and writes as itself, in the project or the directory of it the call names (`cwd`).
  - **What is held is the run's**: the time a call may take (`timeout`, ten minutes without it — the agent is told to stop, given five seconds, and stopped, with what it had said), and that the agent and what it started are gone when the call or the run is over. Its process group is the run's as a shell command's is.
  - **What it says it used is recorded and not held.** It is the agent's own account: not counted by the runtime, not under the run's budget, not in what the run used of a model. In the journal it is a record of its own kind under the call (`outside-usage`), as each tool call the agent reported (`outside-tool`) and each permission it asked (`outside-permission`) is; `trama journal` shows them under the call, and says the two sums apart at the end. (A cost is said by an agent as the protocol has it — what its conversation has cost so far — so of each conversation the last counts, once; tokens are a turn's, and are added up.) Of the variables an agent is started with, a journal keeps the names.
  - **What this lets out, said plainly:** money — an agent is heavy before it does anything, and nothing caps it — and whatever the agent does under the user's login with every permission granted, as a shell command can already. A validation (`create`, `update`) calls it for real, as it does a shell command and pi's agent — in the copy the program is tried in, so what the agent writes there is not the project's; what it spends, and whatever it does beyond that directory, is real, once for each time the program is tried.
  - **It works where a harness works: `workspace.agent(prompt, { agent, … })`.** The same call — its options, its result, what is held and what is on record under it — with the agent at work in the run's workspace, or a directory of it, as `workspace.shell` is `tools.shell` there. `tools.agent` holds the agent to the program's own project; and every place a harness is put to work is a workspace — a run pointed at a codebase, the copy a writer is handed, each task a loop runs a harness on. So an agent from outside could be asked a question and could not be given a job. On the record it is a call of the workspace's (`/workspace/agent`); the agent is the run's to stop, has the run's variables, and is one the run's configuration names. A workspace a host makes (`createWorkspace`) has it too.
  - **`examples/harness-by-agent`** is a harness that is somebody else's, as a program of some twenty lines: it hands its `task` to the agent its arguments name, at work where its run works, and ends with what the agent said and how its turn ended. Run as `examples/coding-harness` is, it sits where that sits — pointed at a codebase, judged by a checker, held against another harness on the same work, or named as the harness of `examples/write-by-harness`, by which an update is written by an agent from outside. What such an agent says it used is its own account still: a judge that goes by what a run used cannot go by it.
  - Not yet: a program's own tools handed to such an agent, a typed answer, images in a prompt.
- **A recorded run can be replayed: `trama replay <name> [run]`, and `replayProgram({ projectDir, run?, loose?, program? })` on the runner surface.** The project's program — or one given in its place — is run again with each of its calls answered from the journal of an earlier run, and none carried out: nothing is asked of a model, no command runs, nothing is written to the project, nothing is spent. A program is to a large degree what its answers make it, so what a replay tells is how far the program goes the way it went, and where it first goes another. It is the first thing to read a journal back.
  - **It is a dry run, and whole as one.** Every answer is the record's, so the program is consistent with itself — what it reads is what the record says was read — and the world is not touched. An effect is not on record, only its answer is: so a replay does not go on for real where the program leaves the record. It ends there.
  - **A call is the recorded one where its endpoint and its request say the same** — whatever order a request's fields are in, and without what is the client's own way of carrying a call (the id its tools are asked by, the id a run it asks for can be stopped by). Calls are matched in the order the record has them; those that were in flight together may be made again in any order. The first call that is not the next on record, or that the record cannot answer (it was never answered, or was too large to keep whole), is where the program has left: it is stopped, and the result says at which call and what was other (`left`). With `loose`, a call is answered wherever its endpoint is the recorded one, whatever it asks — "does it get through what was answered" in place of "does it ask what was asked" — and each request that was other is listed (`other`).
  - **Tools of the program's own are asked again.** An agent call that had them is not only its answer: in between, the program was asked and did things. In a replay the program is asked what it was asked, in that order, and what each tool answers is held against what it answered: a tool that answers otherwise is the program leaving its record.
  - **What a program says to its own run is carried out** — `ctx.log`, `checkpoint`, `done`, `yield` — in a throwaway copy of the project, from the state the recorded attempt began from and with the arguments the run was started with. So a replay has an end, which is held against the recorded one (`sameEnd`; two failures are the same end, whatever their words). `same` says all of it at once: the whole way, nothing asked otherwise, the same end. `trama replay` exits 0 on that, and 1 otherwise.
  - **A run the program asked for is answered from the record, and not started** — nor is a project made or changed. (Its word that such a run is to stop is said of that call, and is no call of its own: in a replay nothing is in flight to stop.)
  - **A program does not choose where it is run.** A replay runs it in a copy, and a fix was recorded in one: so what it asks by its own place — a path made from its working directory, a project named beside its own — is read as asked from the project's place before it is held against the record.
  - **Of a run that was repaired, the last attempt is replayed**: the program that came of it.
  - **A replay is not a run**: it leaves no journal, uses no budget, and changes nothing the project holds. What the replayed program prints is shown under `[replay]`.
  - **A program can be held to every run on record: `trama replay <name> --all`, `replayAll({ projectDir, loose?, program? })`.** Each run of the project that is over is replayed by itself; one whose record does not say what a replay has to begin from is passed over, and said (`notReplayed`); and there is one answer for all — `same`, where every run that was replayed went as recorded and at least one was. A record is a test nobody wrote, of the way its run went and of nothing the run did not do: this is the check for a change that is meant to change nothing — a refactoring, a dependency, a new version of the runtime. (It is no check of an `update`, which is asked for so that the program does otherwise: a changed program leaves a record where the change first shows.)
  - **A program asks for a replay as it asks for a run**: `replayProgram` and `replayAll` from `@trama-dev/runtime/runner`, within a program, are made by its runner. It is the run's own — stopped when the run ends or the program's `signal` says so, given what the run was started with, the program's clock stopped while it waits — and a call on the run's record (`/project/replay`). A validation makes it for real, since it carries nothing out; and where the asking program is itself replayed, it is answered from the record like any call. So a harness has it as an instrument: a project asked for a fix (`repairWith`) can hold what it mends to the run that failed — named by the `journal` it is handed — before it answers.
  - **Without a run named, the latest that is over is replayed.** A run that is still going is not: a program that replays its own project is answered from the run before it. A run that is named is replayed though it is going, as far as its record has got.
  - **What takes a program off its record, said plainly:** anything it puts into a request that did not come across the bridge — the clock, its process id, chance, a file read by `fs`. Such a program leaves at the first call that shows it; a replay says where and does not mend it. A program that runs until it is stopped is not ended by a replay before its timeout.
- **A run can be checked, by a project: `checkWith`.** That a run ended as done is its program's own word, and says nothing of what the work is worth. Where a run names a project to check it — `runProgram({ projectDir, checkWith })`, `trama run <name> --check <project>` — or its own project does (`"checkWith"` in its `meta.json`; a path there is said from where the project is), that project's program is run once the run is done, and what it ends with is the verdict: `{ ok, score?, notes? }`. It is the result's `check`, with who gave it.
  - **A check is no part of the program it checks.** What checks is to stay the same while what is checked changes — that is what makes two versions comparable — and a program is what an update and a fix rewrite. So the checker is a project of its own, named by whoever asks for the run or by the project.
  - **The checker works in a throwaway copy of the project as the run left it**, as its workspace, and is handed as arguments `result` (what the program ended with), `args` (what the run was started with), `journal` and `run` (the record of the run it checks, and its id). What it does in the copy is thrown away with it: a check changes nothing. It is a program like any — a shell for tests that were held back, a model to judge by, a replay to hold the program to its record, which it can be: the run it checks is named, and is replayed though it has not ended.
  - **It is a run of the checked run's own**, as a fix asked of a project is: counted in its budget, stopped with it, started with its variables, with a journal of its own in the checker's project. It is not fixed where it fails, and not checked in its turn.
  - **`done` stays `done`.** A verdict is said beside how the run ended, and does not change it: `status` is the program's word, `check` is the checker's. Nothing acts on a verdict — a run that is done and not good is not fixed, and nothing is taken back: what to make of one is for whoever asked. `trama run` shows it in a line and ends with 1 where the work was not found good.
  - **A check that could not be made is said as that** — `check.error`, and no `ok` — and never as a verdict: a checker that failed, did not end its work, ended with no verdict, was refused for the budget, or was stopped with the run.
  - **Who checked is on record by what it was**: the `check` record of the run's journal, and the result's `check`, have the checker's place and the hash of its program as it was (`by`, `program`), beside the verdict, how long it took, and what it used of a model. `trama journal` shows it, and counts what it used in what the run used in all.
  - **Only a run that is done is checked**: not one that failed or yielded, not a validation (`create`, `update`), not a replay.
  - **What this does not keep, said plainly:** a program out of its checker's reach. There is no boundary: a program has the machine, and can change the checker's project as it can anything. What there is, is that it shows — a checker that was changed has another hash.
  - `examples/check-by-command` is a checker to begin from: good where a command ends well.
- **A project's history is a lineage: every program that is run is a version on record, every run leaves a line in it, and a version can be gone back to.** History had each program `create`, `update` or a repair made, and nothing of how any of them did; a journal has that, for twenty runs. Now the two are joined, and kept: `trama history <name>`, `trama rollback <name> <version>`, `readHistory(projectDir, { runs? })` and `rollbackProject(name, version)` on the runner surface.
  - **A program that is run is a version.** Where a run begins and `program.ts` is not the text of the latest version — written or changed by hand — it is put on record as one, reason `found`. So every run is of a version, and whatever was run can be gone back to: also the program a repair replaced, which until now was nowhere where it had been written by hand. Each line of `history/index.jsonl` has the hash of its version's text (`sha256`).
  - **A line a run: `history/runs.jsonl`.** Written by the runner when a run is over, whatever came of it: the run's id, when it began, the version it was of (and the one it ended as, where a fix was installed, with which attempt worked), how it ended and the first line of why where not as done, what its check said (who, by hash; the verdict; the beginning of the notes), what it used of a model by the runner's own count, how long it took, a mark of what it was started with (a hash of what its program was given — the arguments it was asked with, laid over those the project's own `meta.json` says: runs with the same mark had the same), and what the runner made it for where it made it itself (a fix, a check). Nothing of the work: that is the journal's. Not for a validation or a replay, which are no runs. A line that cannot be written is a warning, and never the run's failure.
  - **The runs on record are the latest.** The file is put aside when it comes to a megabyte (`runs.1.jsonl`, in the place of the one put aside before) and a new one begun: there are always the last thousand runs or so, and never more than two megabytes of them — history is part of a project, and goes into every copy made of it. Versions are not cut: a rollback needs them.
  - **`trama history <name>`** shows each version — its number, why it came, when, the hash of its text, what it was made for — and how its runs went: how many, how they ended, how long they took and what they used on the mean, and the verdicts of each checker by themselves (a checker is told by where it is and by the hash of its program: verdicts of two are never counted together). `--runs` lists each run. It counts and takes means; it says of no version that it is the better.
  - **`trama rollback <name> <version>`** makes that version's text the program again, as a new version (reason `rollback`, with which it is of): history only grows, and a rollback can be gone back on. The program as it is now is put on record first where it is not, so nothing is lost by it. **Nothing is run, and nothing validated** — it has no effect but the program's text, and costs nothing — and nothing else of the project is touched: its state and its files are as they were, and the old program meets them at its next run.
- **A project says what it takes and gives: `description`, `parameters` and `returns` in its `meta.json`, in the words a tool is declared in.** Until now a project said nothing of itself but the prompt it was made with, and a program read its arguments by a cast. What is said is held by the runner, and is told without the program being run. A project that says none of it is held to nothing, as it was.
  - **A run whose arguments do not fit is not begun.** The run's arguments, laid over the project's own, are held to `parameters` before a program is started for them: nothing is asked of a model, and the refusal says what is wrong and what the project takes. An argument written as text where a number or a boolean is declared is read as one — from a command line every argument is text. **An argument the project does not take is left out, and said — not refused**: it does not reach the program (as what a tool does not declare does not, nor what a run gives beside what its project says), so that a version cannot lean on what its project does not say it takes; it is on the run's record (`left-out`), and said aloud where nobody's program asked for the run — a name written wrongly looks the same. A refusal for what is missing names what was left out. Whoever checks the run is handed its arguments as they were asked. (Refusing them would have kept whoever starts a run from ever handing it more: a runner its checker, a loop its harness an input's `id` that is for the judge.)
  - **What a run gives is held to `returns`** at `ctx.done`, as a typed answer is held to its shape: the declared fields and no others are the result, and a result that does not fit fails the call — in the program, before anything is settled, so that a program that goes on can still end its run, and one that ends there has failed and can be fixed as a run that failed is.
  - **It is the project's, and not its program's**: what whoever writes or fixes a program did to `meta.json`, in the copy it worked in, is put back before the program is tried there and is no part of what is kept — and it is said. So what a program is held to, and who checks it, is out of the reach of whoever rewrites it. A version's line in the history has a mark of the contract it was made under (`contract`): versions made under one can be held against each other.
  - **It is changed by whoever asks, and gone back from: a version is a program and what the project took and gave when it was made.** `updateProject(name, prompt, { description, parameters, returns })`, `trama update … --contract <file>` (each of the three that is said takes the place of the project's, whole; what is not said is as it is): whoever writes is told what the project is to take and give from then on and cannot change it, the new program is validated under it, and the two are the project's together or neither is. `addVersion` and `trama add-version --contract` put a version on record under what it is made to take and give, and the project's own is not touched. The text a version was made under is kept with it (`history/contracts/`, by its mark), and:
    - **`trama rollback` goes back to both** — the program, and `parameters` and `returns` as they were when the version was made — and says so (`contract: "back"`); where that is on no record (a version from before texts were kept) it goes back to the program alone and says that (`"unknown"`). What the project is for (`description`) is no part of a version.
    - **A run of a version is held to what the version was made under** (`--at-version`, `runProgram({ version })`), and so is its check and its replay: a version with another interface can be tried beside the program before it is the program.
    - **What a project takes and gives, changed by hand, is a version found when the project is next run** — the same program under another contract — as a program changed by hand is: it is on record, its runs are its own, and it can be gone back to. `trama history` says of a version where it was made under something else than the one before it.
  - **`describeProject(name)` and `describeProjects()`**, from `@trama-dev/runtime/runner`: what a project is for, what it takes and gives — as its `meta.json` writes them, and as JSON Schema. A program asks its runner, and what it was told is on its run's record. `trama list` shows a project's description where it has one.
  - **The notation shapes are written in has two words more**, for a typed answer and a tool's parameters as for these: a field written with a `?` at the end of its name may be absent (`{ "model?": "string" }` — its name is `model`; a `null` under it is its absence), and `"json"` is any value.
  - **The examples say theirs** — those a runner starts in a role among them: `examples/check-by-command` and `examples/repair-harness` say what a checker and a fixer are handed, which is where to read it.
  - **What a run gives beside it is left out, and said** — as of an argument the project does not take: the fields a result had and the project does not name are on the run's record (`left-out`, with `result`: each by where it was — `also`, `lines[].extra`), and said aloud where nobody's program asked for the run — a run by the command line, a program being validated. Until now they were dropped and nothing was said: asked to have a project give one thing more, an update came, the run was done, and the thing was not there. `trama journal` shows what was left out, of the arguments and of the result.
  - **It is born with the project's program.** Whoever asks for a project says what it is to take and give — `createProject(name, prompt, { description, parameters, returns })`, `trama create … --contract <file>` — and it is in the project's `meta.json` before anything is written: whoever writes the program is told it and cannot change it, and the program is validated under it. What of the three is not said so, whoever writes the program says, once, in the `meta.json` of the copy it works in — those three and nothing else of the file — and it is the project's from then on. What is no shape is no contract, and no project comes of it; nor of one that requires an argument the project is not made with (a project is validated by a run of it with its own arguments).
- **A project's history is an archive: a version can be put on record without becoming the program, and a run can be of any version.** A project ran one program, the one in `program.ts`: to hold two versions against each other they were installed turn about, or put in two projects. Which of a project's versions is the program is now one fact among them.
  - **`updateProject(name, prompt, { install: false })`** writes a version and keeps it beside the program: validated as an update is, on record with `aside: true`, and `program.ts` not touched. **`{ from: version }`** has it written from that version, and not from the program as it is. An update now answers with the version it made (`{ version }`).
  - **`addVersion(name, source, { parent?, detail? })`** puts a text on record as a version, beside the program: for a program that writes programs by a way of its own. It is validated, and not mended: on record as it was handed over, or not at all.
  - **`runProgram({ projectDir, version })`, `trama run <name> --at-version N`**: a run of that version's program, with the project as it is. The program is not touched; the run's line and its journal say which version it was of; it is checked as any run is, and **not fixed where it fails** — a fix would be a version nobody asked for. **It is run where the program is**: its text is put in the project's directory for the run, in a file of the run's own (`.trama-run-….ts`, taken away when the run is over), so that what is beside the program is beside it — a module it imports by a relative path is found, as it was when the version was validated. (What is beside the program is the project's, as it is when the version is run: a version is its program's text.) And a replay of a run that was of a version is of that version, where it replayed the program as it had come to be.
  - **A version becomes the program by being gone to** (`rollbackProject`, `trama rollback`), as a version more: so it was, and so it is of a version that was kept beside the program.
  - **A version's line says which it was written from (`parent`)**: of an update, the version the program was — or the one that was named — and of a fix, the version that failed. A line written before this is read as written from the one before it. **A run's line says which models did its work (`models`)**: calls, tokens and cost by the model that served, the runs it asked for among them. A version found good with one model is not thereby good with another, and until now nothing on record could have said which it was.
  - What this leaves to whoever asks: a run of a version meets a project's state it may not have written, and may run beside a run of the program in one directory — as a version gone back to already could. And a replay of a run of a version replays the program as it is, unless it is told which (`program`).
- **An update can be asked of a project: `updateWith`.** What `update` asks of a model was one call in the kernel — pi's agent, under a prompt written there. It is now "whoever writes": pi's agent as before, or a project that is named — in the configuration (`updateWith`), of a call (`updateProject(name, prompt, { updateWith })`), on the command line (`trama update … --with <project>`). As a fix has been since `repairWith`.
  - **The writer is a program like any, run with the copy of the project as its workspace** — the project as it is, what it says of itself (`meta.json`) and its state with it, its program the one that is written from — handed `{ prompt, program, kept, types, copy }`, and answering `{ program }`: the whole of the new one. Anything else is no update, and said as one.
  - **What is done round the writing is the runner's, whoever writes**: the copy, the validation, the version on record, what is installed or kept beside the program, what is kept of what was made beside it. So that a program is replaced only by one that was validated does not come to depend on the program that writes.
  - **It is handed the least**: not where the project is, nor its history, nor the records of its runs. What more a writer is to read, whoever asks for the update says in the prompt — a loop that holds inputs back decides so what its writer can reach.
  - **Its run is the asker's own**: counted where the update is counted and held to that budget, stopped with it, on a record of its own that the asking run's names; its line in its own project's history says what it was for (`for: "update"`), and the validation's record says who wrote and what that took (`written`). It is not fixed where it fails. Its time is its own project's.
  - **A project may be written by itself.** A project is not asked to fix itself, for it is the one that is broken; nothing is broken here, and what a writer writes of itself is validated as any update is.
  - **`examples/write-by-harness`** is a writer to begin from, some seventy lines with their comments: it words what is asked, has a harness do the work in the same copy (`examples/coding-harness`, or the one its own arguments name), and hands back `program.ts` as the harness left it. A better harness is then a better writer — and the coding harness, through it, updates the coding harness.
  - **`examples/improve-by-check` takes `write`**: the project that writes its updates.
  - **pi's agent, asked for an update, is told what the project says it takes and gives**, where it says: the program is held to it.
  - **A candidate that fails its validation is fixed by whoever the configuration names to fix** (`repairWith`), under the update's count — where it was pi's agent whatever the configuration said. With a writer and a fixer named, an update asks nothing of pi's agent.
  - **And so a project's first program: `createWith`** — the configuration, `createProject(name, prompt, { createWith })`, `trama create … --with <project>`. The writer works in the copy of the new project — its `meta.json`, and no program — and is handed no program; its run's line says `for: "create"`. The example writes both: with no program handed it words a making, tells its harness to say in `meta.json` what the project takes and gives, and shows it the example programs pi's agent is shown (`example-programs.txt`, beside it and its own).
  - Not yet: a validation says of a new version of a writer — or of a fixer, or a checker — that it loads, and no more: such a project is run in it with nothing to do.
- **The command line has what the API has of the archive and of what a project says.** `trama update <name> <prompt> --from <version>` and `--beside` (written from a version that is named; kept beside the program and not installed). `trama add-version <name> <file>` (`-` for standard input; `--parent`, `--detail`): a program written by whoever has a shell — an agent from outside among them — put on record as a version beside the program: validated, then run by its number (`trama run --at-version`) and gone to (`trama rollback`). `trama describe [name]` (`--json`): what a project is for and what it takes and gives — every project, without a name — for whoever is to choose among programs. **`trama run … --json`**: what the run came to — its status, its result, its check — as one document on standard output and nothing else there (what is said as the run goes is on standard error): until now the command line told its caller that a run was done and not what it gave, which was in the run's journal alone. A run that was not begun has no document. `trama history <name> --json`. Without `--json`, `trama run` shows what the run gave after what was said as it went. **`trama api`**: what a program is, for whoever writes one themselves — an agent with a shell among them: where a project is, what a program has and how it takes and gives, how what a project takes and gives is written (with one written out), the runtime's API as a writer is shown it, and programs to go by. The help of `create` says how a contract's file is written and that a parameter the project requires is to be given by `--arg` (a project is validated by a run with its own arguments). `trama create … --with <project>` and `--contract <file>`.
- **The loop, as a program: a program can hold a project's versions against each other and keep the better.** It could already ask for a run with a checker and be handed the verdict, and ask for an update. What it lacked is two things, and they are all the kernel adds: a project's history as its run's record has it, and a version gone back to. Which version is the better is no part of trama: it is said in a program.
  - **`readHistory(projectDir, { runs? })` is asked of the runner** where a program calls it. They are files, and a program could read them — but asked for so, what it read is on its run's record, and a replay of the run is told what the run was told and not what the history has come to since. `runs` is for the latest so many: a call's record has room for a megabyte.
  - **`rollbackProject(name, version)` is asked of the runner**, as an update is: the project is changed there, it is said under the run's name, and it is a call on the run's record. A validation ends where its candidate asks for one, as where it asks for an update; a replay answers it from the record, and goes back to nothing.
  - **`inputMarkOf(projectDir, args)`** is the mark a run's line has (`input`), for a program to find the runs on record that were started with the same — and not pay for what is there.
  - **`examples/improve-by-check`** is the loop: some hundred lines, to be read and changed, one round a run. It finds out how the program does — by a judge (`check`), on inputs that are named, from the record where the verdicts are there — asks for an update with what was found wanting — written and kept beside the program — finds out how the new one does by runs of that version, and makes it the program where it is the better: the project never holds a program that was not yet judged, and a round that comes to nothing leaves nothing to put back. Its rule is ten lines from its top: more runs found good; where as many, the higher mean score; a tie goes to the one before. Inputs can be held back (`heldBack`): run and judged as the others, never shown to the model that writes the update, and where there are any they alone decide. It stops without deciding where the update came to nothing or a check could not be made, and puts the version before back where anything goes wrong while the new one is tried.
  - It is for a project that is given arguments and ends with a result: the runs are of the project in place. A project that is itself the work — a codebase one run changes for good — needs a fresh copy for each run, which this does not make.
- **A harness can be improved over tasks: it is a project of its own, and each run of it works in a fresh copy of a task.** Three small things, on what the loop already was:
  - **A checker is handed where the run worked** (`workspace`, among its arguments) where the run had a workspace. It has a copy of the project for its own workspace as before — but of a run that worked in a workspace, the work is not in the project.
  - **`examples/coding-harness` works in its run's workspace where the run has one**, and in the project it is the program of where not, as before. So a harness can be a project by itself, pointed at a codebase run by run: one harness, many pieces of work, each a run of it — on its record, and of one of its versions. And `--arg model=provider/model` has another model do the work than the project's own.
  - **`examples/improve-by-check` takes `from`**: a directory that is copied afresh for every run and is that run's workspace (`{name}` in it stands for an input's argument: `from=/tasks/{task}`). Every run of every version begins from the task as it was; the copy is removed once the run is judged. A run's mark is of its arguments and not of where it worked, so the verdicts are found on record round after round as they are for runs in place.
  - **And the loop finds a program's verdicts by its text, not by its version's number.** A version gone back to is the program it was under a new number, and a round after one that kept nothing made every run of it again. (Found by a trial with real models: eight runs paid for twice.)
- **A version can be found the better by what a run uses, with the work held good.** Where the work is done right already, there is nothing to improve by how often it is: what differs is what it takes.
  - **A checker is handed what the run had used when its check began** (`used: { calls, tokens, cost }`, among its arguments): the runner's own count, the one a budget is held by — a record may be cut short or not kept, and what the check itself uses is no part of the work.
  - **`examples/improve-by-check` takes `by=score`**: a version is kept where its mean score is higher, provided it is no less often good — counted over every run there is, those of inputs that are shown too. **`margin`**: by how much a score has to be higher (a measure is never a tie: without one, a version no different is kept one round in two). **`confirm`**: where a version passes, the runs that decide are made again and counted with the first — a version is chosen by the runs in which it looked best, and is to be kept for more than those. **`tell=all`**: the writer is told what the judge said of the runs found good too.
  - **And a round of the loop knows what the rounds before it came to.** A version that was not kept left nothing a writer could see: the next round began from the same program, asked in the same words, and was answered with the same idea (seen in a trial with a real model: three rounds, one idea). The writer is now told of each version that was written from the program as it is, judged and not kept — what its runs came to and what it changed, as a diff (its first 20,000 characters); a version that was never judged whole (a check of it could not be made) is not told as one that was tried. It is read from the project's history, where a version's line says which it was written from and its runs say what the judge found: the loop keeps no list of what it tried. And what the judge said of a run is told whole round after round: the loop keeps it in its state, where a line of history keeps its first two hundred characters — which had left the writer of a later round with less to go by than the first.
  - **And a run that failed is not a verdict on the version.** The loop counted a run that failed as a run not found good, at a score of 0, whatever had failed it — and went back from a version, with a real model, because the model could not be reached for two minutes (and told the rounds after that the version had been tried and found worse). A run that fails is now made again, once, and the second counts; where that fails too, a round over a version being tried decides nothing — the program stays, and the round after is told of the version as written and not judged, with what the run said as it failed (nothing of it where the run was of an input held back). Of the program as it is, a run that fails twice is a run found wanting, as it was. The result says how many runs were made again (`remade`).
- **A run's record says what state the run began from**: the `attempt` record has it (`state`). A replay begins there. Journals written before this can be replayed only where the run began with no state.
- **Whoever is asked for a program can say that there is none to be written.** An answer of pi's agent that begins `NO PROGRAM:` is that, and no program — as one that begins `NO FIX:` is of a fix: `create` makes no project and `update` leaves the program as it is, whoever asked is told why in the answer's own words, and nothing is validated or handed to whoever fixes. Until now the one thing a writer could answer with was a program, and an answer in words — that what was asked went against what the project says it gives — was tried as one: it could not be read, and a fix was asked of that, which wrote a program in the writer's place or said in its turn that there was none. (A project that writes — `createWith`, `updateWith` — says it by failing, with its reason.)
- **`trama api` says how a run's arguments and the project's own lie**: what a run is given is laid over what the project was made with (`trama create --arg`), which it is also validated with — so a parameter the project has an argument of its own for is never missing from a run, required or not.
- **A command that was stopped at its time says so: `ShellResult.timedOut`.** There only where it is so. Until now the one sign was that `stderr` ended in a line "timeout" — as a command's own may — so a program that had to know went by a clock as well, which no replay can answer. The two example harnesses go by the field now.

### Fixed

- **Several runners at one project at the same moment no longer fail for what another of them was doing.** A project is not one runner's alone: a session's participants begin together, and so may any two runs of it. Of 120 first runs of a project, six at a time, 38 had failed — `EEXIST … symlink`, `Malformed package.json`, `Path cannot be followed` — and, with no first run in it, a path was refused now and then while another runner put a new file in its place, which is how the state is saved at every checkpoint. Three things were made in steps, or looked at in steps, that another could come between:
  - **The links to the runtime** (`node_modules/@trama-dev/…`) were looked for, and then made; and one that led elsewhere was removed, and then made — so for a moment there was none, where another runner's program was resolving it. A link is now asked once what it says, and where it is to be another, made beside its place and moved into it: the place is never without one, and runners at the same moment each put the same link there.
  - **`package.json` and `.gitignore`** were written into: emptied, then filled. A runner reading one at that moment read the beginning of a file. They are now put in place in one move, by the one rule the state already went by (written beside the place and moved into it; a file hands on its permissions, a link to it stays the link, a file closed to writing is not replaced; where nothing can be made beside it, it is written into as before).
  - **The guard of a path** takes two looks — its own walk, and the system's reading — and refuses a path where they do not say the same. A file made between the two, or a new one put in its place, and they did not: `Path cannot be followed … (the system does not take it where its links say)`, for no fault of the path's. Looks that differ are now taken again, and the path is refused for it only where they differ at each of eight readings. That is as good as certain and is not certain: nothing lets a process take both looks at one moment.

## 0.8.0 — 2026-11-22

### Added

- **A program can ask a model itself, one reply at a time: `agent.complete({ messages, system, tools, … })`.** No agent is at work behind it — no tool is run, nothing is asked again, nothing is remembered. The program keeps the conversation, reads in each reply why the model stopped, runs the tools the model calls and sends back what they said: it is the harness. `agent.instruct` and `agent.generate` are as they were, with pi's agent as theirs.
  - **A message** is the user's (`{ role: "user", content }`: text, or parts of text and images), a reply as `complete` returned it, or a tool's result (`{ role: "toolResult", toolCallId, toolName, content, isError? }`). A request is held to that before anything is asked or counted, and what is wrong with it is said by where it is (`messages[2].toolCallId is the id of the call it answers…`): pi holds a conversation to nothing.
  - **A reply** is plain data — it can be kept in `ctx.state` — and goes back into `messages` as it came: it holds what its provider wants to see again. What a program may read of it is declared (`ModelReply`): `content` (parts of text, of thinking, and tool calls with their `id`, `name` and `arguments`), `stopReason`, `usage`, `model`.
  - **`stopReason` is the program's to read**: `stop`, `toolUse`, `length` — a reply cut off at its limit is a reply, with what there was of it — and `error`: a provider's failure, or one that did not answer in time, comes back as a reply with `errorMessage`, asked once. Whether to ask again is what a harness decides. What is not the model's doing fails the call: a request that is none, a model pi has not got or has no key for, a level the model does not think at, a budget that is spent, a run that was stopped.
  - **Tools are declared and not run.** The same object `instruct` takes (`name`, `description`, `parameters`); its `run` may be there or not, and nobody calls it. The model's arguments come back as it wrote them.
  - **What goes with a request is a short list**: `model` (`"provider/model"`; without it the project's, which is then one pi has or the call fails — there is no agent whose own choice to fall back on), `thinking`, `maxTokens`, `temperature`, `toolChoice` (`"auto"`, `"none"`), `timeout` (five minutes without it). No headers, no keys, none of a provider's own options.
  - **It is a call to a run's budget**, admitted or refused as an agent's is and counted for what its reply used, by pi's price list. A loop makes one for each turn, so it is better held by `tokens` or `cost` than by `calls`.
  - **In the journal**: the request, the reply, and a `usage` record, as of any call; `trama journal` shows each by the last that was said in its conversation.
  - **A run that was given variables has its requests asked with them** — by the process that asks the models of such a run's agents already — so a key that is among them is the key used.
- **A fix can be asked of a project, in place of pi's agent: `repairWith`.** In `~/.trama/config.json` (`{ "repairWith": "my-fixer" }`: a project by its name, or by a path) or for one run (`runProgram({ projectDir, repairWith })`). Where the run's program fails, that project's program is run with the copy of the failing project as its workspace; it is handed `program`, `error`, `journal` (the path of the failed run's record), `kept` (whether what it changes beside the program reaches the project) and `types` (the API as an author is shown it), and answers with `{ program }`. What the runner does round a fix is as it was: the fix is tried in the copy, and what was changed there reaches the project only with a program that then runs. Without `repairWith`, pi's agent is asked, as before.
  - **It is a run of the failing run's own**: what it asks of a model is counted in that run's budget (each request it makes is a call there), it is stopped with that run, held to the same time, started with its variables — and has a journal of its own in its own project, which the failing run's journal names (`trama journal` shows `the fix is asked of a project: run …`). What it used is on record there.
  - **What fixes is not itself fixed**: where the project asked for a fix fails, or answers with no program, there is no fix, and the run says why. A project is not asked to fix itself.
  - A project named that is not there is said before the run begins.
  - **What it used is said where the fix was asked for, too**: the failing run's `fix` record has `by` (the project) and `used` (`calls`, `tokens`, `cost`), `trama journal` shows it on the fix's line, and it is in what that run is said to have used in all — as what pi's agent uses for a fix is.
- **Whoever is asked for a fix can say that there is none.** A program that cannot be made to run and still be the program it was — a check that cannot pass, where the only "fix" is to take the check out or hand the failure back as a result — is not to be "fixed" so. pi's agent is told to answer with a line that begins `NO FIX:` and says why; a project asked by `repairWith` answers `{ unfixable: "why" }`. The run then fails with that (`No fix came back: It was said that there is none to be had: …`), the `fix` record is marked `none`, and nobody is asked again. Before, an agent's refusal in words was taken for the program: installed in the copy, run, and — failing to parse — asked for again.
- **`examples/repair-harness`**: a harness that fixes programs, written as a program — the loop, the tools the model has in the copy, asking again where the provider failed, what is made of a reply that was cut off or of a call that is not what a tool declared. In the repository to begin from, not in the packages: copy it among your projects and name it as `repairWith`. Every request it makes and everything its tools do is in its journal, line by line — which a fix by pi's agent never showed.
- **`examples/coding-harness`**: a harness for work on a codebase, as a program — what `agent.instruct` has pi's agent do, with the loop in a file of some three hundred lines: tools for the project it is in (list, read whole or by lines, write, edit one passage, shell), asking again where the provider failed, and a conversation that has grown long kept within what the model reads (by its own count, or when the provider says the conversation is too long): what old tools said forgotten, and the work summed up where that is not enough. To begin from, like the other.
- **`workspace.shell(command, { cwd?, timeout?, env? })`**: a shell in the workspace, as `tools.shell` is one in the project — for a program whose work is in a directory that is not its own. `cwd` is a path within the workspace. On record as `workspace/shell`.
- **`heldTo(parameters, given)`**, exported beside `ctx` and the rest: what a model called a tool with, held to the parameters the tool declared — the declared fields and no others, or an error that says what is wrong in words the model can be handed. What the runner does for an agent's tools, for a program that runs its own.

### Changed

### Fixed

- **The example harnesses gave a shell command a time the model was not told of**, and what ran into it came back as a command that had failed: 300 seconds in `examples/coding-harness`, 120 in `examples/repair-harness`. With a real model at work on a codebase whose tests take minutes, nine commands were stopped so and made again, and nearly all of a run's time went there. The `shell` tool of both now takes `seconds` — the model says how long each command may take, up to 1,800 (600 for a repair) — says so in its description, with what to do about more (start it in the background, and look in on it), and says of a command stopped at its time that it was stopped, with what it had printed.

The harness now keeps one of its own: a sum of what is in each of the codebase's files when the work begins, and from it the files that are not as they were — whichever tool changed them, a command of the shell's as much as an edit. The model is told it after the latest answer cut, each time something is forgotten (and beforehand, that it will be, and to go by it); and the run answers with it, `files: { changed, made, gone }`, beside what the model says it did.

Now nothing is forgotten unless that brings the conversation back; where it does not, the work so far is summed up — one request to the model, with no tools — and goes on from the task, the summing-up, the record of the files and the latest turns as they were; and where neither would do, the run fails and says what the least of it comes to. The run's answer says how often each was done (`forgotten`, `summed`).
- **The record `examples/coding-harness` keeps of the files it changed had what is built in it**, as much as what is written. It leaves out what the codebase's `.gitignore` leaves out (asked of git; everything, where git is not to be had).
- **`examples/coding-harness` forgot by how many answers there were, not by their size**: it kept the latest twelve of what tools had said whole, which by themselves are some 48,000 tokens — more than it was to keep to, where a model reads little. It now cuts the oldest answers until enough characters are gone to bring what a request reads back to six tenths of `forgetAt` (measured by what the provider said the last request read), keeps the latest two whatever their size, and forgets half of what was sent where a provider says a conversation is too long.
- **Two tests leaned on the shell they were run from.** "PiAdapter warns once…" expected pi to have no model to fall back to, and failed with a provider's key set; "a run is held to its budget…" expected a run given no budget to have none, and failed where `~/.trama/config.json` has one. Both now keep to an environment of their own.
- Tests for what none had asserted, the code being right: a directory beside a project whose name begins as the project's does is outside it; a link by full path to a place outside a directory says in a copy what it said; a GIF of the older kind and a WebP are images, and what only begins like one is not; of what a tool returns, only nothing at all is "Done."; a journal goes twelve names deep.

### Fixed

- **What a call's host says it used is held to what a count is.** A call with extensions is served in a process of its own, and an extension there has the host's channel: a count on it whose figures were no numbers (`{ used: { input: "x", … } }`) made no number of what the runner itself had seen the call's replies use, and the budget counted no number as nothing — a call could be made to cost its run's budget nothing. A count is now every figure a number and none less than nothing, or it is no word of a host's and is passed over; what the runner saw stands.
- **What a host says of a call is said with the call's number, and heard by that call alone.** A host serves one call after another, and what it says while nobody listens waits on the channel for whoever listens next: a late word of one call — its answer, what it used, a request to have its model asked — was the next call's. Every word of a call, and every request it would have its runner make of a model, now names its call, and the runner hears only what is the call's own. And a host that is asked to serve while it is at a call's work still — something else in its process answered for it — ends, rather than serve two: that is one call's failure, and the next has a host of its own.
- **What a host started in groups of their own is asked to stop, and given its time**, when the host is ended: the host used to end them at once (SIGKILL) as soon as it was asked to end itself, while its runner was giving the same groups five seconds — an MCP server under a host had no time to put anything away.
- **A shell command does nothing before whoever watches for its runner knows of it.** `tools.shell` started a command and then listed its process group, to be stopped with the run — or by the watchdog, should the runner die. A runner that died in between left a command that was already at its work, and on nobody's list: it ran on (seen as a test failing once in some dozen full runs on Linux — the test stops the runner the moment its command has begun). A command's shell now waits to be told that it is listed before it becomes the shell the command is run by; where its runner is gone first, nothing of the command is run. (To the command nothing is different: the same process, `$0`, arguments and output.)
- **A project's state is put in place whole.** `ctx.checkpoint()`, `done()` and `yield()` wrote into `state.json`: a program stopped in the middle of that — a timeout, Ctrl-C — left half a state, and every run after refused to start (`Corrupt state.json`). It is written beside the file and moved into its place, as a program is: the state before, or the new one. A state file made read-only is still not replaced. (In a project whose own directory allows no file to be made in it, the state is written into its file as before: there is no other way to it there.)
- **What is to take a file's place is its writer's alone while it is written**, where it is handed the permissions of what it replaces: it stood with the permissions any new file has until it was whole — the new text of a `0600` program or artifact readable by others for as long as the writing took.
- **Versions of a project recorded at once each have a number.** Two runs of one project that each recorded a version (a repair in each, say) could both take the same next number: one failed — and after a repair that failure was passed over, so a fixed program was installed with no entry in its history. The one that finds its number taken takes the next.
- **A pattern is matched in one way, and not in every way.** `workspace.list` and `observe` handed a pattern to the system's matcher of expressions, which tries every way a path's directories could be shared out among the pattern's parts: a pattern that says `**/` a dozen times, against a path some twenty directories deep, was not done with in minutes — and nothing else the runner serves was served meanwhile. Patterns match what they matched (held against the old reading on a hundred and forty thousand made-up cases), with one difference: `**` now also crosses a line break in a file's name, as "any run of characters" says.
- **Smaller, of the bridge and the tools:**
  - A use of a program's tool that is still waited for when its agent call ends is done with (it has the answer of one that was not waited for), where it stayed waiting for good; whoever asks what is next of a call that is over is told that nothing is, where they were held until their connection ended; and a program's client that cannot ask waits longer each time before it asks again (up to a second), where it asked twenty times a second.
  - `runProgram()` in a program with a `timeout` or `maxRepairAttempts` that is none, and `tools.fetch` with a header that is no text, are the request's fault, said before anything is done (they failed later, as the runner's own failure).
  - A name of the agent's said twice in `tools` beside a tool of the program's (`["read", "read", { … }]`) is not refused: only a tool of the program's by another's name is.
  - Whoever hears what a call used and throws (`sofar`, `had`: internal) has said nothing, where a throw failed the call's every later request; a model that was to be asked for a call cancelled meanwhile is not asked; a call that cannot be sent to its host fails as it is handed over, and nothing is said of it after.
  - A typed answer that is fenced, and holds fences of its own in what it says, is read whole, where the model was asked a second time for it.
  - What `tools.fetch` returns is cut at ten megabytes of what was sent, where it was cut at ten million-odd characters — three times as much, of text in three bytes a character.
- **Smaller, of the CLI and of projects:**
  - `trama run` and `create` refuse an `--arg` with no name (`--arg =x`) and one given twice, where the first was taken and the second silently won; `--arg __proto__=x` reaches the program, where it was dropped.
  - A failed run is said to have failed once (`Error: Program failed (repair disabled): …`), where the reasons that say so themselves had it said twice.
  - A project's name is one line of text: a line break or another control character in it is refused. A project reached through a link in `~/.trama/projects` is listed, as it could already be run; a file there by a name is no project to `run`, `update` or show the logs of.
  - `createProject(name, prompt, { model })` in code refuses a model that is no text before it makes anything, where it wrote it into the project's `meta.json`, which no run could then read.

- **A relay that is closed has pi let go of what it kept for the sessions it asked for.** Where a model is asked by a call's runner (0.6.0), pi keeps things for the session in the process that asks — for `openai-codex` an open WebSocket — and the relay was to have them let go of when its run is over. It never did: pi's way to do that was looked for as a package to be required, pi-ai is one to be imported and nothing else, and the error was passed over as "nothing to let go of". Such a socket stayed open in the runner until pi's own idle time closed it (five minutes). It is looked for where pi looks, by what the package exports to an `import`; a test has a relay asked for two sessions and closed.

## 0.6.1 — 2026-11-19

### Changed

- **What an extension asks a model for itself is asked by the call's runner too**, where it was asked by the process that serves the call: a request by the options of the model's own provider (`ctx.modelRegistry.complete`, `.stream` — how pi's own example extensions ask), an image (`generateImages`), a classifier's word (`classify`). What each used is then read where no extension is, as it is of the agent's own requests. A provider's options are its own and are not known by name, so the rule is by what they are: a request is handed over where everything that goes with it is plain data — text, numbers, lists and records of those — and asked where the call is served, as before, where something is not, or is the asker's own to ask by (a function such as `onPayload` or `onResponse`, an `apiKey`, a `fetch`, a date, an object of a library's). A reply that is to be fetched later (`deferred`) is asked for and fetched where the call is served.
- **An image, a classifier's word, and a reply fetched later are the call's as a reply is**: counted as they come, waited for where an extension asks as its session ends, and stopped when the call is cancelled or the time pi gives a request is up. They were said before they were asked, and no more. A request that is refused — the call cancelled, or out of budget — ends saying so (`The call is to ask no more.`), where an image or a classifier's refusal said the provider had no such thing. To have a provider give up a reply it was keeping (`cancelDeferred`) asks no model, and is refused nobody.

### Fixed

- **A request an extension makes as pi's agent does (`streamSimple`), with a function of its own in it, is asked where the extension is.** It was handed over without the function — `onPayload`, `onResponse`, `onProviderStreamEvent`, which were then never called; a `transformHeaders`, whose headers the request was then asked without. What is left out of a request that is handed over is what is known to be nothing a provider is handed: pi's own hooks (the very ones the session's agent has), which do nothing where no extension listens for the four provider events; and, of a request the agent makes for itself, what its loop calls as a turn goes.
- **A name with nothing under it is what it was where a request is asked by the runner.** An option such as `headers: { "x-configured": undefined }` or `samplingParams: { top_p: undefined }` takes a header, or a parameter, of the model's own out of a request; handed over, the name was lost on the way, and the model's own was sent. (And what an asker makes of a request's headers is seen by that too: a `transformHeaders` that only takes a name out, or moves one, has made them other than they were.)

## 0.6.0 — 2026-11-18

### Added

- **A call says how it is served.** `agent.instruct(prompt, { model, thinking, tools })` and `agent.generate({ …, model, thinking, tools })`: the model for this one call, as `"provider/model"`; how much it is to think; and the agent's tools — exactly the ones named, `[]` for none. (A `generate` with `tools: []` is made from its prompt alone; without the option it is served as it always was, by the agent with its own tools, which may read and run things to find the answer.) Each is honoured or the call fails. pi takes a thinking level it does not have for the model and serves the call at another, drops a tool name it does not know, and reads `"re*"`, `"+grep"` and `"-bash"` as patterns and changes to its own choice — all without a word; trama looks at what the call was given before the model is asked, and refuses what is not what was asked for. A model named by a call that pi's catalog does not have is an error too (the project's own, if unknown, is still a warning and pi's fallback). What a provider makes of a level pi does offer is beyond that check: for some models two levels come to the same request. These options were passed over until now, like any field the bridge did not know: a program that already gave them is now held to them.
- **A typed answer may hold lists and objects.** `agent.generate` took a flat schema of `"string"`, `"number"` and `"boolean"` fields. A field may now also be an object of fields, or a list — written as the shape of its items, in brackets: `{ passed: "boolean", failures: [{ test: "string", line: "number" }], tags: ["string"] }`. The answer is held to the shape at every depth, and holds the declared fields and no others; where a reply is not of the shape, the model is told where (`failures[1].line: expected number, got string`) and asked once more, as before. A schema that names a kind in a word trama does not know (`"string[]"`, `"array"`) is told how a list and an object are written. (Of a value that is not of its kind, the message now says `got null` and `got a list` where it said `got object`.) The types are exported as `Schema` and `SchemaField`.
- **`create` and `update` ask for the program where the project can be looked at.** The agent that writes a program worked in an empty directory: asked to `trama update report "use the columns of data/sample.csv"`, it could not see the file. It works in a copy of the project now — the same kind of copy a fix is asked for and tried in — and is told so. What it reads there is the project's, and what it makes there is not lost (next entry). (The copy shields the project's own files, as it does where a fix is asked for: what a link in the project leads to outside it is the same place from the copy.) Two things come with working there. The agent is asked as the project's own agent is: pi reads the project's `AGENTS.md` and `.pi/` (a system prompt, settings) from where it works, so a project that has them now steers the writing of its program too — as it has always steered the agent a fix is asked of. And the copy is made before the model is asked: a second or more for a project of many thousands of files, during which the command does not answer to Ctrl-C (as during the copy a validation makes).
- **What the agent makes beside a program is kept with the program.** A program was one file, because the program's text was all that was taken from the agent that wrote or fixed it: it could not install the package the program imports, write a module or a fixture beside it, or put right a config file the program fails on — a crash that was the project's and not the program's could not be repaired at all. Now the agent works in the copy the program is then tried in, and what it changed there reaches the project with the program, on the condition anything reaches it on: the program ran.
  - *A fix.* The agent's answer is put where `program.ts` leads in the copy as the agent left it, and tried there: what the agent did and what the run did are merged together, or neither is. A fix may leave the program's text as it was and mend the project. If the agent left a link at `program.ts`, the answer is written through it, over what it leads to — a module of the project, if that is where it pointed the link — and that path is named among what changed. The agent is told that its work is kept, and told where the journal of the failed run is (the project's own, which it can also write to). Where the agent left its copy with no place for a program, not to be read, or moved it away, its answer is tried by itself in a fresh copy, as it used to be, and the run says that nothing else of the agent's work is kept.
  - *`create` and `update`.* The candidate is validated in a copy of the agent's copy — so that what the validation run does stays out of it — standing among what the project stands among, not among what the agent made beside its own copy; once the program is installed, the agent's copy is merged in. The program is the agent's answer, validated where it will be installed: what the agent left at `program.ts` where it worked, and what that led to, stays there, and a link it put at the name — or took away from it — is undone for the validation. (Where it changed the way from the name further along — a link on it made to lead elsewhere, a directory on it replaced — the candidate is validated by itself, as below.) A candidate that does not pass takes none of it into the project — in `create` too, which leaves the candidate to be looked at without what was made for it. Where the agent's copy cannot be copied to validate in — it left a file nobody may read, or moved the copy away — the candidate is validated by itself, in the project as it is, and the command says that nothing else of the agent's work is kept. (What a copy that *can* be copied makes of a run is the validation: a `state.json` the agent left broken fails the candidate, where the candidate alone used to be tried.)
  - *Not during a validation.* A fix asked for while a candidate is validated is the program alone, as before, and the agent is told that: nothing else of a validation is kept, so a fix that leaned on what its agent did beside it would be installed without it.
  - *Said, and recorded.* The paths the agent changed where it worked are printed, the first ten of them (`[trama] the agent asked for the fix changed 3 path(s) beside the program: config.json, helper.mjs, stale.txt`), and for a fix are in the journal's `fix` record, the first two hundred with how many there were. What of them did not reach the project — somebody was at the place meanwhile — is said after, as it is for a run's work. `history/` keeps versions of the program only.
  - **This changes what `create`, `update` and a repair may do to a project**: files other than `program.ts` — trama's own among them (`state.json`, `meta.json`, `history/`), deletions included — by an agent's judgement. `"agentChanges": "discard"` in `~/.trama/config.json` takes the program alone: a fix is tried where the agent never worked, and the agents are told that instead.
- **What is beside a project is beside its copies.** A program that read `../shared.json`, imported `../lib/helper.mjs` or ran the project `../worker` ran — and could never be repaired, or validated by `update`, because the copy a fix or a candidate is tried in stood alone in a temp directory. A copy now has, beside it, a link for each name beside the project: `..` leads from the copy where it leads from the project, for the trial of a fix, a validation, and both agents. What is reached that way is the real thing, as the workspace is and as an absolute path always was — **so a validation's writes through `..`, which used to land in the temp directory and vanish, are now made, and so are a failed fix's.** That includes the project itself, by its name from there: a module in `../lib` that writes `../my-project/data.txt` writes the real file, whatever becomes of the trial. What it does not do: reach further up than one level; show what is in a directory that may be passed through but not listed; or make or remove *names* beside the project — a file made as `../new.txt`, or `rm ../shared.json`, is made or removed beside the copy and goes with it (a repaired run, and `create`/`update`, say so; a validation's own run does not). What is done *through* a name is done to the thing: `rm -rf ../shared/` empties the real directory. And it costs a link for each name beside the project at every copy: nothing among dozens, seconds among tens of thousands.
- **`env` for a command, a run and a participant.** `tools.shell(cmd, { env })`, `runProgram({ …, env })` and `session.spawn(name, { …, env })` give variables over the runner's own. A run's variables are its program's, its commands', its agents' and those of the runs it asks for, each of which may be given more. An agent of such a run is served by pi in a process of its own, started with the run's variables: what it finds of pi (`PI_CODING_AGENT_DIR`, `HOME`), the key it has for a provider, and what the commands it runs are given, are the run's. (That process loads pi at the first call it serves — a second or two — and calls made together have one each; a run that was given no variables has its agents served in the runner, as before, unless a call asks for extensions.) What a program sets in its own `process.env` is still not handed on by itself — that has been so for participants since 0.3.1 and for `tools.shell` always — but it is now one word to hand it on: `env: process.env`. The journal records the names and never the values (and of a name that is none because it has a `=` in it, not what follows the `=`). A variable given as `undefined` is one not given; `TRAMA_PORT` and `TRAMA_INIT`, by which a program finds its runner, are passed over whoever gives them, each program having its own. What is given is taken as it is when the call is made: an object changed afterwards changes nothing, for a participant that is resumed too. **`Session.spawn`, and `runProgram` called outside a program, used to pass over an `env` they were given; it is now applied, or — where it is not an object of names and text — refused.** Not given: a way to take a variable away; variables for `create` and `update`, which validate with the environment `trama` was started in; variables for one agent call apart from its run's.
- **The shell that runs a command is the runner's.** `tools.shell` started `sh` by the `PATH` the command was to have — which a command can now be given: one without `/bin` on it found no shell (`spawn sh ENOENT`), and an empty one ran whatever was called `sh` in the project. The shell is found by the runner's own `PATH`, and the `PATH` given is the command's. The shell is still `sh` to itself and in what it says (`$0`, `sh: no-such: command not found`, `spawn sh ENOENT`). And a command the system refuses to start outright — more environment than it will hand a process — is a result (`exitCode: 1`, the reason in `stderr`) like any other failure to start; it was an error of the call. (A *run* given more than that still cannot be started, and says so.)
- **A program's calls reach its runner whatever proxy its environment names.** With `NODE_USE_ENV_PROXY=1` and an `HTTP_PROXY` in its environment — the runner's, or now a run's — a program on a node that honours those for `node:http` sent every call to the proxy, the bridge's secret with it, and took the proxy's answer for the runner's. The bridge has an agent of its own, which goes straight there.
- **A call may keep an answer that was cut off.** `agent.instruct(prompt, { cutOff: "keep" })`: an answer cut off at the model's output limit is returned as far as it went, instead of failing the call (see "Changed") — where there was anything of it; a reply cut off before its first word still fails. `generate` takes the option too, and holds what was kept to its schema like any reply: a cut-off answer is seldom whole JSON, and is then asked for once more. For a call whose work is what the agent did with its tools — the default would throw that work away over a closing summary that ran long, and a repair would start it again.
- **A call can have what you set your pi up with.** An agent call was served by pi with none of it — no skills, no extensions, and a prompt never read as one of your templates — and a program could not ask otherwise. `agent.instruct(prompt, { skills, templates, extensions })`, and `agent.generate({ …, skills, extensions })`:
  - `skills: true`, or a list of names: the skills pi finds for you and for the project (its `.pi/skills` and `.agents/skills` among them; of two by one name, the project's). The model is told of them and reads the one it needs; a prompt of `instruct` that begins `/skill:name ` is that skill's text and, after it, the rest. pi tells a model of its skills only where it has `read` or `bash`: a call with skills and neither is an error, where pi would have served it with none.
  - `templates: true`, or a list of names: a prompt that begins `/name` is your template of that name (or the project's, in `.pi/prompts`), with the rest as its arguments, split as a shell splits words. `instruct` only: what tells the model how a typed answer is to be written follows the prompt, and a template may leave out what follows its name.
  - `extensions: true`: your pi extensions — those of your pi directory and settings, and the ones pi has built in, its MCP support among them: the MCP servers in your `mcp.json` are the agent's. `extensions: "project"`: the project's own as well (`.pi/extensions`, the servers of `.pi/mcp.json`). Their tools, which a call's `tools` can then name — an MCP server's too (`mcp__server__tool`, where the server shows its tools to the model): with extensions, the tools a call names are looked for when its model is first about to be asked, and a call that names one nobody has fails there, the model not asked. Their commands, one of which may ask the model and have its answer be the call's; what they do to a session, the skills and templates they bring among it. They are told when the session begins and when it is over. With `true` an extension that asks is told the project is not a trusted one; with `"project"` that it is.
  - **A call with extensions is served by pi in a process of its own** (`agent-host`) — as is every agent call of a run that was given variables — started when a run first makes such a call, kept for the calls that follow one another (calls made together have one each), and ended with the run. An extension is somebody's code: in the runner it could hold up or bring down every run of a tree, and reach what counts and stops them. What it gets wrong now ends its process and fails the one call it was serving — a call that is held is given up by its process after three seconds, which says what it used and serves on; a process that will not let go of a cancelled call is given five, then ended with what it started (also what it started in process groups of their own — an MCP server, a command of the agent's — while the system can still say whose they are: by its `/proc` where it has one, by `ps` elsewhere — and where the runner itself is gone, its watchdog ends each such process with what is under it, as it ends a program's group; a program's own detached children are still the program's to leave), and the call is taken to have used what the process last said it had; one that ends by itself fails the call with how it ended; the next call starts another. What the call has used is said before a model is asked again on its account, and the model is not asked before the runner has answered: a budget stops a call in another process where it would stop one in its own. Such a process loads pi at the first call it serves, which takes that much longer (a second or two on a quiet machine). The process that serves a call still answers for that call's answer; what the call used is read by its runner where the runner asks its model (below), and is that process's word where it does not.
  - **trama stands where pi asks a model.** pi asks one in more places than its agent's turns — for a summary, to keep a provider's cache warm while a session waits, and for an extension that asks by pi for itself — and all of them come by one step, where a request is made ready for its provider. There a call is asked whether its model may be asked again (what it has used so far is said, and whoever counts may stop it), there a call that is cancelled, or whose session is gone, is refused, and there what a reply used is seen. So what an extension asked for itself is in its call's count, where it was in nobody's (a reply is counted once, by the account of usage it carries: a provider of an extension's own that hands on a copy of another's reply, account and all, is counted twice, and one that uses a single account for all its replies, once) — as it is told that its session is over, too, which is why a call now says what it used when its extensions have heard that out, and not before; a warm-up request is said before it is made, where it went out unseen; and nothing is asked on the account of a call that is cancelled, or whose session is gone. A call that has its answer is not stopped for what it has used: what an extension would ask beside it, the budget being spent, is refused, and the answer stands (`sofar` is told that the call has its answer, and whoever hears says no instead of cancelling). Whoever counts is told as each reply comes (`had`), and not only when the call next asks or is over: calls made together under one budget know sooner what the others have used. And **an extension that is asking a model as its session ends is waited for**: the five seconds an extension is given to hear of the end are its own time, and the time a model is at work on what it asked is not counted in them — where a call came back after five seconds whatever was being asked, and the request went on in the process that served it, counted by nobody (or, asked by the runner, was cut off there). A model is given for it what pi gives a request of its own (`retry.provider.timeoutMs`, else `httpIdleTimeoutMs`: five minutes by default), after which what is still being asked is stopped, and what it had used by then counted; a cancelled call's requests are stopped at once, an extension's own among them. So a call whose extension sums the session up comes back when the summary is written, and not before. And what an extension asks as it is told that its session *begins* is its call's from then — said before it is asked, counted, held to the budget — also where the call fails before its agent was set going (it named what its model has not): such a call said nothing of what it used.
  - **The model of a call that has extensions is asked by the call's runner** (`model-relay`): the process that serves the call hands each request over and is handed the reply as it comes, so what the reply used is read where no extension is — a count its process says is taken for no less than that — and a run that was given variables has one more process, started with them, do the asking. Where an extension has a hand in the asking (a provider it registered; `before_provider_request`, `before_provider_headers`, `after_provider_response`, `provider_stream_event`; its process's variables or its ways to the network made other than they were; a request it makes for itself with a provider's own options, by `stream` or `complete`), or the runner's pi has not the model as the call's has it, or the request holds what cannot be sent, the model is asked where the call is served, as before, and the count is that process's word. Of a long tool call an extension that watches a reply come is shown the arguments as of a little before (they are handed over whole as they grow by half, not with every piece). Not a wall: pi does not hold an extension to it.
  - A name pi has no skill or template by is an error that lists what it has. `false` or `[]` is the option left out, and a call that leaves all three out is served exactly as before. `create`, `update` and a repair take none of them.
- **A run can be given a budget.** `trama run <name> --budget cost=2.50 --budget calls=40`; `"budget": { "cost": 5, "tokens": 2000000, "calls": 200 }` in `~/.trama/config.json`, for every run given none of its own and for each `create` and `update` (writing the program and validating it, together); `runProgram({ …, budget })` and `session.spawn(name, { …, budget })`. `cost` is US dollars by pi's price list, `tokens` all that the model read and wrote, `calls` how many calls to an agent are taken on. A run given a budget of its own has that and not the config's.
  - It covers all a run causes: its program's agent calls, each request for a fix, and what the runs it asks for use — those are held to every budget above them as well as to their own, so a program can give a run less than it has and never more.
  - Once it is spent an agent call is refused (`The budget is spent: $2.0134 used of $2.`), and a program that fails is not repaired — a fix is asked of a model too. A call under way when a cap on cost or tokens is reached is stopped where a model would be asked again on its account — its agent for a turn or a summary, pi to keep a provider's cache warm, an extension for itself; the request in flight is let finish, so a run ends over its cap by the requests in flight when it was reached. The first time a call is refused or stopped it is printed — once for a run, the projects made for its program included; a journal has a `budget` record before its last where its run ended with a budget spent or had a call refused or stopped for one, and a run's own caps in its first. A run that is not recorded (`journalRuns: 0`) now waits, like one that is, for the calls it cut off to say what they used — where a budget holds that to anything.
  - Counted in the runner, where every call to a model passes, not read back from the journal. A guard and no wall: what a program spends by other ways than the runner's agent calls is not seen, and what pi cannot count is counted as nothing: `calls` is the cap that holds there.
- **What writing a program used is said, and recorded.** The request `create` and `update` make for the program happens in no run, and what it took was nowhere. It is printed (`[trama] writing the program used 3410 tokens  $0.0212`) — also where the writing failed, was stopped, or ran into the budget — and is the first `usage` record of the validation's journal, `for: "generate"`, counted in that journal's total.
- **What agent calls used is in the journal.** Each time the agent behind a call was asked, a `usage` record says which model served it, the tokens in and out and through the cache, and the cost by pi's price list — written when the call is over, however it ended: a call that failed or was stopped half-way has used what it used, the request that was cut off included, and a run's journal does not end before the calls it cut off have said so. Each fix asked for has one too. `trama journal` shows it on the call's line, and a run's total on its last line and in `--list`.

### Fixed

- **A call's answer is the model's last reply, as it happened.** It was read from the conversation as pi would next show it to the model — and pi takes a failed reply out of that. So a call whose last request the provider refused as too long, or whose last reply was cut off, came back with whatever the model had said the turn before (`"Let me look at the file first."`) as its answer, or as `Empty response from LLM` where there was no turn before. The answer is read from the session's record now.
- **A provider's refusal is the call's error.** A request the provider refused or could not serve — a bad key, a model it will not run, a request it calls invalid or too long — ended as `Empty response from LLM`, the reason lost: pi ends such a run quietly, with the reason in the last message, and only its text was read. The call now fails with `The model did not answer:` and the provider's own words. So does a reply pi itself holds to have failed though it has text — a stream that ended without saying how — which used to be returned.
- **An option that bears the name of what a call is made with no longer takes its place.** `agent.instruct("the prompt", { prompt: "another" })` asked the other prompt, and `tools.shell("echo this", { command: "echo that" })` ran the other command: the options were laid over the arguments. Such an option is refused where the call is made (`command is what the call is made with, and cannot be given as an option`) — also a `dir` or `pattern` given to `workspace.observe`, and an `id` given to `runProgram` from a program.
- **A prompt that begins like a pi command is still a prompt.** `agent.instruct("/review the diff below")`, on a machine whose user has a pi prompt template called `review`, sent the model the template's text in place of the program's. A program's prompt is passed to pi as text and nothing else.
- **What comes back for an agent call after its program has ended is not recorded as an answer.** The rule was there and held for a shell command; an agent call is cancelled faster than the bridge sees the program's connection close, and its `Aborted` went on record as what the program had been told.

### Changed

- **An option a call does not take is refused.** The bridge passed over any field it did not know: `tools.shell(cmd, { stdin })` and `agent.instruct(prompt, { tool: ["read"] })` were carried out as if the option had not been given, and said nothing. Each is a `400` now — `Unknown field: tool (this call takes: prompt, system, model, thinking, tools, skills, extensions, cutOff, templates)` — and the program is told at the call. An option whose value cannot be sent (a function, a symbol: `tools.shell(cmd, { onOutput })`) was dropped on the way; it is refused in the program before anything is sent, as a number JSON cannot carry already was. (A field given as `undefined` or, where it is optional, as `null` is still a field left out. A `Session`, and `runProgram` called outside a program, are not held to this.)
- **An answer that was cut off at the model's output limit fails the call** (`The model's answer was cut off at its output limit.`), unless the call keeps it (`cutOff: "keep"`, above). It used to come back as if it were whole — or, where pi had taken it out of the conversation, as whatever the model had said the turn before. A reply cut off in the middle of a tool call was never the end of a call, and is not now: pi has the model make the call again.
- **A cancelled agent call has pi abort its run** rather than throw the session away: what the request in flight had taken by then is counted. A recorded run that cut a call off waits for its backend to let go of it before the run is over — a few milliseconds with pi, at most the five seconds a program that ignores being stopped is given.
- **A program has a project made or changed by its runner.** `createProject()` and `updateProject()` called in a program did their work in the program's own process — a runner of its own inside the program: outside the run's budget, on nobody's record, not stopped when the run was, its validation under no watch. They are calls on the bridge now, as `runProgram()` has been: carried out by the one runner of the tree, counted in the run's budget and not in the config's a second time, a call in the run's journal with the validation's journal named beside it, shown under the run's name, validated with the run's variables, and stopped with the run or when the program no longer wants it (`signal`). The program's clock goes on meanwhile: a project made is the program's own work.
  - *What a program loses,* each found by running the same program before and after:
    - The project is written by an agent of the run, as any of its agent calls is served: with the runner's pi and environment, and over them the variables the run was given (`env`). What the program set in its own `process.env` once it was running — a provider's key, `PI_CODING_AGENT_DIR`, `HOME`, a proxy — no longer says with which pi, which keys or under which home the project is made, nor do the writing agent's own shell commands have it: what a run is given when it is started does. The candidate's validation has the run's variables.
    - An error comes with the bridge's words before it (`trama runtime error: Error: Project "x" already exists.`).
    - The call is held to what it takes, as every call on the bridge is: an option it does not know is refused where it was passed over (`{ bogus: true }`), and so is an `args` that holds what cannot be sent — a function used to be dropped from it, and the project made.
    - What is printed of the making (`Generating program for…`, `Created…`) is the runner's, shown under the run's name; it is no longer the program's own output, so it is not in the `exit` record's `stdout`, nor in the failure a fix is asked with. The run's journal has the call.
    - A candidate being validated that would have a project made or changed no longer does (below).
  - *A validation ends where a candidate asks for one*, as where it asks for a run: `create` and `update` used to make the inner project for real while they validated the outer program, model and all — and `trama run` then found it already there.
- **Backends hear more in a call** (`AgentCall`, internal): `skills`, `templates` and `extensions`, each to be honoured or rejected; `asText`, for a prompt that is not to be read for what it begins with (every `generate` with skills or extensions); and `sofar`, where a backend whose agent asks its model more than once says what the call has used before each asking after the first — for a turn, or for pi's summary of a long conversation — and whoever hears it may cancel the call there. (A request pi retries by itself before anything was counted is asked again with nothing said: there was nothing to say.) `createBackend` takes the meter a run counts in, and gives every call a `sofar` and a `used`.
- **The two agent calls no longer take the same fields**: `/agent/generate` refuses `templates` as a field it does not know.
- **Backends hear `model`, `thinking`, `tools` and `used` in a call** (`AgentCall`, internal). A backend that cannot honour one of the first three is to reject; one that cannot know what a call used, or a call that used nothing, says nothing. A final reply that was cut off is rejected with `CutOff`, which carries what there was of it.

## 0.5.0 — 2026-11-15

### Fixed

- **A file could be written outside the project through two links.** With `first` a link to `second`, and `second` a link to a file outside the project that did not exist yet, `tools.write("first", …)` created that file. The guard followed only one link whose destination was missing, and looked for the nearest existing directory with a check that cannot see such a link — so a path below a directory link pointing outside and at nothing passed too. It now follows every link on the way to a path, whether or not what it points at exists, and refuses links that lead back to themselves. `workspace.write` was not led outside, but through a chain of links it replaced the link in the middle with the file; it now writes where the chain ends.
- **A file outside the project could be read through a link whose target goes up after another link.** With `here` a link to `.` and `a` a link to `here/../secret.txt`, every link points inside the project as text — but the system takes `..` from where `here` leads, and reads the file beside the project. `tools.read`, `workspace.read`, `workspace.observe`, a `shell` `cwd`, and the runtime's own files (`state.json`, `history/`, `.gitignore`) all went by the text. The guard now walks a path the way the system does, one step at a time, and `workspace.list` resolves links the same way, so what is listed is what can be read. A link target that is not valid UTF-8 is refused rather than guessed at. So is a path the system would not follow: one that goes on from a file, says with a closing slash that a file is a directory, leads on from something that does not exist, passes through a link to nothing or a directory it has no leave to search, or follows more than 32 links. The guard now ends by asking the system: where the system can follow a path it must arrive where the guard's own walk did, and where it cannot, that must be because nothing is there yet.
- **A path a program gives is read the way the system reads it.** The guard followed links step by step, but only after the path it was handed had been tidied up as text — so everything it had learned to refuse inside a link was still let through when written out directly. `tools.write("notes.txt/", …)` overwrote `notes.txt`; `write("missing/.", …)` created a file called `missing`; `write("notes.txt/../other.txt", …)`, or the same through a directory with no leave to search, overwrote `other.txt`; and with `deep` a link to `a/b`, `tools.read("deep/../item.txt")` read the project's `item.txt` where the program's own `fs.readFileSync` reads `a/item.txt`. None of these left the project. The path is now walked as it is written, and the check against the system at the end is made of the path as written too. A path that only leaves the project as text — `deep/../../item.txt` above — is no longer refused, since it never leaves it. `tools.shell`'s `cwd` and the workspace calls are read the same way. A link that names a directory of the project in other letters than the directory has, on a file system that takes the two for one name, is no longer refused as leading outside: whether a path ends up inside the project is decided by what the directories are, not by how they are spelled.
- **A pipe, a socket or a device in a project is neither read, written, nor copied.** Three things went wrong with one. `tools.read`, `tools.write`, `workspace.read` or `workspace.observe` of a named pipe waited for whoever was at its other end — and since the runner reads and writes in one step, the whole runner waited with it: every program of the session, its timeouts, and Ctrl-C. So did a run of a project whose `state.json` was one. The guard now lets a path through only if what it leads to is a file, a directory, or nothing yet. And a project that held a pipe or a socket — one a server left behind, say — could not be repaired or updated at all: copying it failed inside Node with an internal assertion, which came out of `runProgram` as an exception. A copy of a project now holds its files, directories and links, and nothing else.
- **A copy of a project is always removed.** A copy carries the permissions of the project's directories — it has to, or a fix could do in the copy what it cannot do in the project — so a project with a read-only directory left two full copies of itself in the temp directory at every repair attempt, and so did a run that closed a directory itself. Removing a temp directory now opens what is closed in it first; the watchdog does the same. A project that cannot be copied — a file in it nobody may read, or a temp directory that lies inside it — is a reason no fix came back, and the run fails with it; it used to be an exception.
- **A pipe that bears a journal's name no longer stops every run of the project.** Making room for a new journal opened each file named `*.jsonl` in `logs/journal` to see whether it was still being written. A journal is a regular file now; anything else with such a name is not listed, read, or removed in its turn. `trama journal` is held to the same.
- **Where the state and the run log go is asked each time one is written,** not once when the run starts: a program that replaced its own `state.json` or `logs/latest.jsonl` with a link or a pipe while it ran was written through, or waited on.
- **The links to the runtime are put inside the project.** `node_modules/@trama-dev` was the one place the runtime wrote without asking where it led: in a project whose `node_modules`, or `node_modules/@trama-dev`, was a link to somewhere else, a run created a directory there, and replaced a link named `runtime` or `session` that was there already. Such a project is now refused, with the path that leads out. (The links themselves point at the installed packages, outside the project, as they are meant to.)
- **What a repaired run did arrives in the project, or is said not to have.** A fix is tried in a copy of the project, and what its run did there is carried back. That used to mean the files it wrote, compared by size and modification time, and it went wrong at every edge of that:
  - A fix that put a new file in the place of a read-only one had the result dropped without a word. A file that may not be written into is now replaced by a new one, with the new one's permissions.
  - A fix that replaced a file by a link, or by an empty directory, had the file removed from the project and nothing put in its place. One that replaced a directory by a file had the directory emptied and the file not written. A directory it made, or removed, a link it made or re-pointed, permissions it changed: none of these arrived, and none was mentioned — so the next run of the installed fix could fail for want of a directory the fix itself had made.
  - A fix that made a directory unreadable (`chmod 300`), or listable but not searchable (`chmod 400`), had every file under it removed from the project: what could not be looked at counted as removed.
  - A change that kept a file's size and put its times back was not seen at all.
  - A file somebody made in the project while it was being copied, and changed again during the run, was overwritten or removed as if it had been the run's own.

  What a run did is now the difference between two readings of a whole tree — files, directories, links, permissions — and a reading says what is at every path or fails; there is nothing it skips. A file counts as changed by the system's own record of its last change, which no program can set. Each difference is carried over if the place in the project — and the directory it is in — is still as it was when it was copied, and otherwise reported: printed as a warning and recorded in the run's journal (`trama journal` shows it). All of that is found out before anything is done, so what is reported as not arrived is as it was, there and under it; a directory the run removed, or put something else in the place of, goes whole or stays whole. Finding out is looking, so a directory that is closed is opened for it, as it is for what is then done in it, and left allowing what the run left it allowing: a run that opens an empty directory nobody could look into and writes in it, or closes a directory it has filled, has that carried over like the rest. One thing a merge does not carry, and says so: a name the run only spelled in other letters (`notes.txt` to `Notes.txt`), where the project's file system takes the two for one name — to a comparison of paths that is one file removed and another made, and carrying it out would remove the file. Which names are one is asked of the project's directory, which lists each name as it has it; what is there under a name the directory does not list is left alone under every name the run changed. What the run moved — a file, a link, a directory — goes from where it was only if it arrives where the run moved it; if that place was taken meanwhile, or is a directory that could not go, or the system will not have it made there, it stays, and both are reported: what it held is not left in neither place. A file the run wrote into is written into, and stays the file it was (so does one whose permissions are all that changed, also where it may not be written to); where the run put another file in the place, another is put in its place. What the project held is recorded in the same pass that copies it. If what the run left cannot be read at all, nothing is merged, and the run says so. Nothing is lost by the merge being done in part. What takes the place of something is made beside the place first — under a short name of its own, so that the longest name a directory takes can still be taken the place of. What is there is then not removed but moved aside, beside the place, and comes back if what was to follow from its going does not arrive — the system refused a later step, a read-only project directory, a locked file, a path too long; only when all of that is settled does it go for good. A directory the run removed goes from its place as one. What the system will not let the merge clean up afterwards is reported under the name it is left by (`.trama-tmp-` and twelve hex digits); a directory the run removed, out of which the system will not remove everything, is left holding that; a file that could not be written into has a new one put in its place, and that is said. What is nothing that can be put in a project at all, like a pipe, is reported. A file is compared and copied a piece at a time, so its size is no limit.
- **A failing fix can no longer write into the project through a link.** A link that named a place in the project by its full path was copied as written and still led to the project, so what a trial wrote through it was written there whether or not the fix worked; so did one that left the project with `..` and came back in by the project's own name, where the temp directory was beside the project — and anywhere else that link led nowhere in the copy, so a program that worked in its project failed when validated or repaired. A link is now copied by what it names, not by how it is written. Most links name the same place from the copy as they are written, and are kept so — including one whose way goes through other links of the project, which the copy has too. One whose way steps out of the project over its top, or into it from outside (by any name the file system has for the project, or by a link outside that leads back in), is rewritten to name the place itself: in the copy, if that is in the project. Where the way of such a link comes to the project and stays in it — by full path, or out of the project and back in by its name — only the part that comes to the project is replaced, and the rest kept: a link of the project on the rest of the way is still gone by in the copy, wherever a run points it next. A link whose way cannot be followed is not carried into the copy: what it would come to name cannot be told. Nor is one the system will not follow, for the number of links on its way or the length of a name — whether it will is asked of the system, not counted — or one whose words, said of the copy, are longer than a link may be. (What is guaranteed is where each link leads. A link to a directory above the project still leads there, and the project can be named from there, as it can by any full path a program writes out.)
- **A link a repaired run makes by its working directory's full path names the project once merged,** not the copy that is gone: the part of what it says that comes to the copy is replaced by the project, and the rest is kept as the run wrote it. So is one that leaves its directory and comes back in by the directory's name.
- **A project that cannot be copied whole is not copied in part.** A directory that could be listed but not searched had its subdirectories left out of the copy without a word, where the project had no journal yet, and a program was validated against a project that was not the one it would run in. It is refused, like any other entry that cannot be read.
- **What a repaired program did to its own file reaches the project like the rest of what it did.** The repaired program is installed and then what its run did is merged. The program's own file was among what was merged, and a fix that removed its own `program.ts` was kept only because the installed file never happened to have the size and time of the one before it. Now the merge is told what was installed — at the place as the project's directories list it, which need not be how `program.ts` or a link spells the way to it — and compares the program's place with that: a program that changed what its file allows (`chmod +x`), that made `program.ts` a link to where it moved itself, or — in a project whose `program.ts` is a link — made it a file of its own, or pointed it at another file, leaves the project as it would have run directly, with what the link led to holding what the run left there. One that removed itself is still the fix that ran, and stays, under the name the project has it by. One whose run leaves a directory, or a link out of the project, where its program was has not left a project with a program: that fix did not work, and nothing of its run reaches the project.
- **What a repaired program made of itself arrives whole, or not at all.** The project is to have a program after a repair, and that was checked in the copy — before a merge that may arrive in part. A fix that made `program.ts` a link to `sub/main.ts`, where somebody had put a file at `sub` meanwhile, left the project with a link that led nowhere, and the next run threw `ENOTDIR`; one that removed the file its `program.ts` linked to, where the file put back in the link's place could not be put there, left the project with neither. What makes `program.ts` lead to the program — the name, each link and directory on the way, the file, before the run and after it, each known by what it is rather than by a name — is now one thing to the merge: if a part of it does not arrive, or a part the run left alone is no longer in the project as it was (somebody removed the file a new link leads to, say), nothing is done at any of them, what was already done is taken back, and the project keeps the fix as it ran. (So that it can be taken back, a program file a fix rewrote is put in place as a new file, as `create` and `update` put one, and is not written into.) It is reported like anything else that did not arrive.
- **A project's own directory is a directory like any in it.** What it allows was no part of what a copy or a merge knew. So a copy's own directory always allowed everything: a program that made a file in a project whose directory may not be written to passed validation, or was repaired and reported done, and failed in the project. And the merge, which opens a closed directory to work in it, did not open this one: in such a project a repaired run's work never reached files that were there and could be written — its own `state.json` among them — though the same run, run directly, wrote them. The directory itself is now in the tree: a copy allows what the project allows, the merge opens it and leaves it allowing what it allowed (or what the run left it allowing, which arrives like any other change), and if somebody gave it other permissions meanwhile it is theirs — nothing is made or removed in it, and that is reported. Since a copy now allows everybody what the project allows them, it is made inside a temp directory that is the runner's alone; it has the project's name there.
- **Where a copy tells names apart that the project takes for one, nothing is done to what is in such a directory either.** With the temp directory on a file system that tells `Sub` from `sub`, and the project on one that does not, a fix that removed `Sub/a.txt` and made `sub/a.txt` had the file removed from the project and nothing put there — reported as `sub` "left as it was". A path through a directory the project takes for another is a path through the other: nothing is done at any, and each is reported. So are two names the run made where nothing was, which the project turns out to take for one: neither is put there. And a directory of the project that somebody spelled anew while the fix ran is no longer the directory the run worked in: a file the run moved out of it, to what the project now takes for the same place, was removed from the project as moved away, and nothing was told.
- **A project whose directory was moved away or removed while a fix was tried is not made anew at its path.** Putting the program in place made the directories on the way to it, the project's own among them: a run left a new directory at the old path holding `program.ts`, what the run wrote, and nothing else, and `update` left an empty one. Where no project is, no program is installed, and that is the error. The same holds for everything else the runtime used to `mkdir -p` its way to in a project: a run's journal, the scaffold, `tools.write`. And a run knows its project by what it is, not only by its path: where another directory has been put at the path since the run started, no fix is asked for, tried, installed, merged or written down there; the run ends saying so.
- **A directory named `program.ts` is said to be one.** A run of such a project failed with `EISDIR` thrown from the runner; `update` and `create` failed the same way after the model had written the program. The run now fails as one whose program cannot be loaded, with no fix asked for; a candidate is not tried, and installing one is refused, each with the reason.
- **`workspace.list` and `workspace.observe` see every alias of a shared directory.** With `a/ref` and `b/ref` both links to `shared`, only the first was listed: the second was taken for a loop, though `workspace.read("b/ref/item.txt")` read it. A link to a directory is now followed wherever it really is, and not where it is come upon by way of another link — which is what keeps a loop from being gone round more than once, and the listing from growing with every order the links can be taken in. A path through two links or more can be read but is not listed; which of such paths were listed before depended on the order the directory happened to be read in.
- **A project's journals stay out of its copies wherever `logs/journal` really is,** and a temp directory inside the project is recognised however it is spelled. Both were found by comparing paths as text: with `logs` a link to another directory of the project, every repair attempt copied the whole journal history; and a temp directory inside the project, named in other letters than the project on a file system that takes the two for one, had the project copied into itself as deep as a path can go.
- **A run's journal could be written beside the project.** The journal directory was worked out with the same textual reading of `..`: with `logs` a link to `x/../..` and `x` a link two directories down, the guard and the system both take `logs/journal` to be inside the project, and the journal went to a directory of that name above it. Nothing in the runtime asks Node where a path leads any more; one walk answers for all of it, and a test keeps it that way.
- **A `create` or `update` that fails while installing the program leaves the project as it was.** The new program is written beside the old one, the version is recorded in `history/`, and only then does the new program take the old one's place, in one move — and if any of that fails, what was done is taken back. Before, `program.ts` was overwritten first: a `create` whose version could not be recorded left a program installed that was not in the history, and a write cut short left half a program. A `program.ts` its owner has made read-only is still not replaced. Taking a version back never removes what another run of the project recorded in the meantime, and a version is never written over a version file that is already there. The message of a failed `update` now says the program is unchanged — which is what it can promise — where it said the project was.
- **`agent.generate` with a schema type it does not support fails before asking.** It used to ask the model, find that no reply could satisfy the schema, ask again, and only then report the schema.
- **A `meta.json` that is not JSON, or has no `input` object, is reported as that,** naming the file and what it needs to hold, rather than as a syntax or type error from wherever its contents were first used. The `model` and `provider` it names are held to what the global config is held to — an empty or mistyped one is an error, not a quiet return to the global model; `null` is a field left out. A file that holds `null` where an object is expected is said to hold null, not "object", and a `null` in `~/.trama/config.json` is a field left out, as it is in `meta.json`.
- **A state that cannot be written leaves `ctx` as it was.** A failed `checkpoint()`, `done()` or `yield()` had already advanced the iteration marker and cleared or set the yield marker in `ctx.state` before the write failed.
- `ctx.log` no longer throws over data that cannot even be described — a circular object with no prototype. And the optimisation loop shown to the model as an example (and in the README) no longer ends in an error when nothing improved: it passed `Infinity` to `ctx.done()`.
- A stop asked for with a signal that had already fired when it was handed over now takes effect; it was only listened for from then on.
- **A repair that worked becomes the project's program before anything its run wrote reaches the project,** and in one move, the way `create` and `update` install one. The order was the other way round: what the run wrote was merged first — `program.ts` among it, copied over in place — so a project that could not take the new program was left with the new state beside the old program. Now such a fix leaves the project as it was, and the run fails with the reason.
- **Once a run has ended, its state is settled.** `ctx.checkpoint()` after `ctx.done()` or `ctx.yield()` is refused. After a yield it erased the marker the next run resumes from, and the program yielded again for ever; after `done()` it rewrote the state the run had ended on. A call that is refused, or a repeated `done()`, no longer takes the state it was handed either.
- **A `program.ts` its owner has made read-only no longer breaks the run that tries to repair it, or the update that validates its successor.** The copy a fix or a candidate is tried in carried the file's permissions, and the candidate was written into it: `trama run` threw a permission error naming a temp directory instead of reporting the failed run, and `trama update` threw the same after the model had already written the new program. A copy's program is now the copy's own file, allowing what the project's allows and its owner to replace it. And whether the project's program can be replaced at all is asked before the work whose only use is to replace it: a read-only program that fails is reported as failed with no fix asked for, and `update` refuses before generating. The same holds for a project directory nothing can be created in — asked of the nearest directory that exists, where the program is a link into one still to be made — and `update` asks before it prepares anything in the project, so the refusal is the one that says why.
- The bridge answers a request whose body is not a JSON object with 400. `null` was a 500, and a string or an array was carried out as a request with no fields.
- **Every field of a bridge call is declared, and held to its kind.** Only some were: a `cwd`, `timeout`, `system`, `headers` or `expect` of the wrong kind went through to whatever used it, and came back as a 500, or as something stranger — `tools.shell` with a `timeout` that was not a number answered with an internal error in the command's `stderr`. They are 400s now, and a field a call does not declare is not passed on.
- **A number JSON cannot carry is refused where the call is made.** `runProgram({ timeout: Infinity })` inside a program crossed the bridge as `null`, which the runner reads as a field left out, and ran under the default timeout — where the same call outside a program is an error. So did `tools.shell(…, { timeout: NaN })`, and such a number anywhere in a run's `args`. The call now fails in the program, naming the field. Log data is the exception it always was: it is recorded as JSON makes of it.
- `workspace.write` that cannot put its file in place no longer leaves its temp file in the workspace, and refuses the workspace itself as an artifact path (`""`, `"."`) instead of briefly creating a temp file beside it. Its temp file is created under a name that cannot be guessed, and never opened if the name is taken: a link planted where the temp file would go used to be written through, to wherever it pointed. A temp file left behind by a runner that was killed in the middle is no longer listed or observed as an artifact, and an artifact that is replaced keeps its permissions. The timeout of `workspace.observe` is measured on a clock that cannot be set.
- **A copy of a project keeps its links where its file system tells letters apart.** A link written `data/input.txt` reads `Data/Input.txt` on a disk that takes the two for one name — macOS, as it comes — and a fix is tried in a copy made in the temp directory. With that on a disk that tells them apart, the link led nowhere there, and a fix that read through it failed in the copy though it would have worked in the project. A name the copy does not have as it is written is now written as its directory lists it; names outside the project, and a link that never comes to it, are left to the letter, and beside the project on the same disk a copy keeps every link as it is.
- **A program's own fences are not taken for the reply's.** The program is cut out of a model's reply by its fence, and a program that showed its usage in a comment, between fences of its own, was cut at the first of those. A reply is now read as a program first: where every fence in it stands in a comment, it was not fenced at all; and a block ends at the first closing fence that is not the program's own. A fence of four backticks around one of three is kept whole. (A comment is one that begins its line, and nothing else of the program is read; where that finds no end to a block, the block ends where it used to.)
- **A model that answers with nothing is not taken to have written a program.** `trama create` made a project whose program was empty — which runs, and does nothing — and `trama update` replaced a program with one. Both now fail, and say so; nothing is created, and nothing replaced.
- **`trama create` and `trama update` can be stopped.** A signal used to end the command where it stood, and `create` left the half-made project behind. Both now stop as `trama run` does: the call to the model is cancelled, a program being validated is asked to stop, and a project that has no program yet is taken away again — the directory that was made for it, and no other that is at its name by then.
- **A command that has ended is not timed out for what it left running.** A `tools.shell` command that started something in the background and exited was reported as timed out if its time ran out in the second its output was still waited for — and likewise as stopped.
- **`tools.fetch` stops reading at 10 MB.** It read the whole response into memory before cutting it down to that.
- **Only what trama wrote is a journal.** Any file named `*.jsonl` in `logs/journal` was listed as a run, and removed in its turn to make room. A journal is now known by its name and by how it begins (one that bears a run's name and may not be read, as another user's run leaves it, is taken at its name). A file of somebody's own among the journals is the project's like any other: it is in the copy a fix is tried in (the fix used to fail for not finding it), and what the fix writes beside it arrives. A journal that has its last record is no longer shown as still running while the process that wrote it lives on; a journal's name appears with its first record in it; a huge `BigInt` is cut like any other long text; and a value that says how it is to be written down (`toJSON`) is asked once.
- **A program that leaves a link out of the project where its program was fails as a result.** `runProgram` threw the guard's refusal instead of returning a failed run with no repair tried.
- **A candidate that fails is refused for how it failed.** Where it had also made away with its own `program.ts`, validation reported that instead of the failure.
- **`agent.generate` takes only a finite number for a `number`.** `1e999` is valid JSON and reads as `Infinity`.
- **`Session.createTemp("")` makes its directory in the temp directory**, not beside it; a prefix that names a path is refused.
- **`workspace.observe` refuses what it could never return**: a path that leads out of the workspace, at once (also when more than one match is asked for, which used to wait out its timeout), and one path wanted as one text as soon as a directory is seen there.
- **A workspace named by a link whose directory is not there is made where the link leads.** It used to fail — also in the middle of a run, at the next attempt, if somebody had removed the directory meanwhile.
- **A pattern is made of what was written and nothing else.** A text that the old pattern compiler used internally matched everything when written in a pattern.
- **Links whose words lead through further links, thousands deep, are refused for what they are.** They were followed until the stack ran out, which was caught further up as "cannot be followed" — the same answer, after ten times the work.
- **A file in `history/` whose name is a number too great to count on from** no longer stops every later version from being recorded.
- **The watchdog is not started with `NODE_OPTIONS`.** What that variable has every node load first — or wait for, a debugger — is the runner's business; the watchdog is a few lines of its own that must start.
- **A state file's `__trama_yield` is a resumption only if it holds a reason.** Anything else under that name was taken for one.

### Added

- **The types of the program-facing API can be imported from `@trama-dev/runtime`:** `Ctx`, `Agent`, `Tools`, `ShellResult`, `Workspace`, `ObserveResult`. The API reference shown to the model has always declared them there; only the values were exported.

### Changed

- **The program a repair leaves is the program as its run left it.** A fix that rewrites its own `program.ts` while it runs is replaced by what it wrote, as it would be in any other run; before, the rewrite was dropped and the fix as the model returned it was installed. Validation in `create` and `update` already worked this way. (The fix is installed as it ran, and what it made of itself is merged in with the rest of what its run did.)
- `tools.write` through a link to a file in a directory that does not exist yet creates the directory, as `workspace.write` does. It used to fail.
- `create` and `update` put the new program in place by renaming a new file over `program.ts` rather than writing into it. The file keeps its permissions; a second hard link to the old file keeps the old content.
- Internal, no change in behaviour: one cancellation helper (`abort.ts`) in place of five hand-written listeners; `ctx.done()` without its in-flight lock, now that persisting is one synchronous step; one reader for `meta.json`; one place that decides where a write through links lands, and one that puts a file in place by temp file and rename (`workspace.write` and installing a program had one each); one guard function, which answers where a path leads (there were two, one answering with the path as given); one function that makes the copy of a project a program is tried in (three places wrote the program into a copy themselves); the runner's side of `ctx` takes the state as an argument of each call that persists it, instead of mirroring the program's `ctx` and being assigned the state first, and is where a run's ending is kept (the runner kept a second record of it); a bridge call's handler is typed by the fields it declares; the guard walks a path on from where its root leads instead of walking the two written together as one string; a project is copied by the runtime's own walk rather than by `fs.cpSync`, whose two implementations disagree about what they copy; one function removes a temp directory, in the runner and in the watchdog; whether two paths are the same place is asked in one way, by what is there (`identityOf`), in the guard, the copy, and the journals a process knows as its own (two names for one project used to let a run remove the journal another run in the same process was still writing) — and it answers "nothing is there" only when nothing is, where it used to answer so whenever it could not look; a project is read in one way (`tree.ts`) by what copies it and what merges into it, which were two walks that disagreed about what a project holds; a link's words are read in one walk for both directions, where a link by full path was read twice and one that is not was read by another rule.
- Internal, no change in behaviour: a copy's links are spelled by asking the guard where each name is looked up, rather than by a walk of `copyTree`'s own; one reader of a journal's first and last record (`inJournal`) in place of three; one way to signal a process group, in the runner and in its watchdog's text; `throwIfAborted`, `messageOf` and `identityIn` in place of their several copies; and guards that could be shown never to fire are gone (a second check for a stopped run before its program starts, a child's "has exited" flag, handlers for a response that ends incomplete).
- **A run asked for under a name another run still has is refused** (and so is an empty name). `runProgram` from a program makes its own names, so this is seen only by one who posts to the bridge directly.

## 0.4.0 — 2026-11-11

### Added

- **The journal: a record of every run.** Each call a program makes through the bridge is written down as it happens — the request when it arrives, the result or the error when it is answered — along with which program was run, how each attempt exited and what it printed, each fix that was asked for and what came back, and how the run ended. One file per run, `logs/journal/<run>.jsonl` in the project, appended to as things happen, so the journal of a run that died is true up to where it died.
  - A repair is recorded as part of the run it repairs, including an attempt whose fix did not work — which used to leave no trace at all, having run on a copy that was thrown away.
  - A session is a tree of journals: the journal of a program says which run each of its `spawn()` calls started, and that run's journal says which call started it.
  - `trama journal <name> [run] [--list]` shows a run call by call, or lists the runs on record.
  - `"journalRuns"` in `~/.trama/config.json` sets how many runs of a project keep their journal (default 20; 0 records nothing).
  - A journal holds what the program did — prompts and answers, file contents, commands and their output. Credential-looking headers of web requests are redacted; nothing else is. It is bounded: a text over 256 KB is cut to its beginning, a record holds about 1 MB and lists what it lost in its `cuts`, and a journal past 64 MB stops taking down calls. Journals are readable by their owner only and live under `logs/`, which is kept out of version control.
  - Recording never changes a run: a journal that cannot be opened or written says so once, and the run goes on.

### Fixed

- **A shell command that reads its input no longer waits for its timeout.** `tools.shell` gave every command an input that was never closed, so `cat`, or anything else that reads standard input, sat until it was killed. A command now has no input and finds it at an end.

### Changed

- When a program fails and no fix comes back, the reason reads `No fix came back: …` after the program's own failure. It used to be a numbered list headed `Repair errors:`, which could only ever hold one entry.
- Internal, no change in behaviour: stopping process groups and the watchdog that does it when the runner is gone are one module; the journal's reader is apart from the runner surface; a run's journal is ended in one place.

## 0.3.1 — 2026-11-11

### Changed

- **One runner runs a whole session.** A program that spawned participants used to run them itself: `Session.spawn()` started a second, complete runner inside the program's own process, which the runner of that program could not see. Starting a run is now a call on the bridge, like any other the program makes, and the runner that is running the program carries it out. `Session`, `spawn()`, `wait()` and `resume()` are used as before. What follows from it:
  - A participant is stopped with the program that spawned it by the runner itself. It no longer depends on that program being able to act: a coordinator that hangs, or is killed outright, does not strand its participants or their shell commands.
  - A participant's output is written by the runner, each line under the participant's name. It is no longer part of its parent's output, and so no longer appears in the parent's failure report or repair prompt.
  - A participant that cannot be run at all — its project is missing, say — makes `wait()` reject as before, but the message now starts with `trama runtime error:`.
  - A participant runs with the runner's environment, not the environment of the program that spawned it. A program that changed `process.env` to affect the runs it starts no longer does.
  - Programs may run programs up to 16 deep, and one runner carries up to 128 runs at a time. There was no bound before.
  - A program that uses a session no longer loads the runner and the agent into its own process. Importing the session layer went from about 0.7 s and 80 MB to about 30 ms and 9 MB (measured once each, on one machine).
- The program that creates a session reaches its workspace through the bridge too, instead of touching the directory itself.
- **`create` and `update` no longer run a program's participants.** Validating a program meant running it to the end — and for a program that runs others, that ran them too: for real, in their own projects, at their own cost, and with a crash among them repaired in place. A participant named by a relative path was not found at all, so a correct program failed. A validation now ends, successfully, the moment the program asks for another program to be run. What the program does after that point is first exercised when it is run.
- **The runner no longer handles signals.** It used to catch SIGINT, SIGTERM and SIGHUP to stop what it had started, and then pass the signal on. That is the watchdog's job now (see below); a process that embeds the runner keeps its own signal handling entirely.
- **`trama run` stops politely on a signal.** The command now handles SIGINT, SIGTERM and SIGHUP itself: the program is asked to stop and waited for, and then the command ends as the signal would have ended it. A second signal does not wait. Ctrl-C used to return at once and leave the program its grace period in the background.

### Added

- `runProgram({ signal })`: aborting the signal stops the run. Its program is stopped, no repair is attempted, and the run ends as failed once the program is gone; a fix that was being tried leaves no trace. A program that exits cleanly on being stopped has still not finished. It works the same from inside a program.
- `runProgram({ label })`: a name for the run, shown in front of each line of its output. `Session.spawn()` passes the participant's name.

### Fixed

- **A runner that is killed outright no longer leaves its programs running.** SIGKILL, running out of memory, a crash: the runner ran no code on its way out, so its programs, their shell commands and its temp directories — one of them holding the bridge secret — were all left as they were. A small watchdog process now holds a pipe from the runner and is told what the runner starts. When the pipe closes, however the runner went, it stops what is still running and removes the directories. (One thing it is not told about: a shell command the agent itself has running at that moment.)
- Shell commands the agent ran on behalf of a participant could read the bridge secret of the program that spawned it. (0.2.2 closed this for `tools.shell()` only.) The agent no longer runs inside that program.

- A cancelled agent call is given up on at once, whether or not the agent itself notices the cancellation. A run's end no longer depends on it noticing.

### Internal

- pi is loaded when the agent is first called, not when the runtime is. `trama list` and `trama logs`, and programs that never call the agent, do not load it.
- The message by which a runner inside a program asked the outer runner to hold the program's clock is gone, with the inner runner.
- The process that saw a stop through after the runner had exited is gone too: the watchdog is that process, started ahead of time.

## 0.3.0 — 2026-11-11

### Changed

- **A participant that is being repaired stays in its session.** Since 0.2.2 a fix was tried against a private copy of the shared workspace, merged back only if the fix worked. A fix could therefore neither be seen by the other participants nor see them, and any participant that writes a request and waits for a reply failed every repair attempt. A fix now runs against the live workspace. The project is still copied: a fix that fails never touches it.

  The cost is that what a failed fix wrote to the workspace stays there — as what a failed first run wrote always has. A workspace write is immediate and is never undone; see the README for what that asks of a program.

- **A program is no longer timed out for the time its participants take.** A program waiting on a session participant had the same five-minute default as the participant, so a participant that needed a single repair outlasted the program waiting for it — which was killed, taking the participant with it. A timeout now limits a program's own time: its clock stops while a run it started is in flight, since that run is under a timeout of its own.

  This changes what `--timeout` means for a program that runs others. It is no longer a limit on the whole session; the participants' timeouts are what bound it.

### Fixed

- **Stopping the runner no longer leaves the shell commands of session participants running.** A stopped runner killed its program's process group outright. But a program that coordinates others holds a runner of its own, which was killed before it could stop what it had started: the participant went, its shell command stayed. A runner now asks first — SIGTERM, then SIGKILL to whatever is still there after five seconds — both for its program and for shell commands, so that anything holding a runner gets to stop what it started. A program that ignores SIGTERM is therefore killed five seconds after the runner is stopped rather than at once.
- **A program has the whole grace period to act on SIGTERM.** Programs were started through the `tsx` command, which put a process of its own in front of the program — one that killed the program about 60 ms after a SIGTERM it had not yet acted on. A program busy for longer than that never ran its handler. Programs are now run by node directly, with tsx loaded into it.
- **A long-running program does not have to handle SIGTERM to be created or updated.** Validation stops a program once it has been ready for a while. Behind the `tsx` command, a program that simply died of that signal looked like one that had exited with code 143, and was rejected — or sent to be repaired.
- **What a program starts itself no longer outlives its run.** Shell commands run through `tools.shell()` were stopped when a run ended; a process the program started on its own, with `child_process`, was not — it kept running after the program finished or crashed, and was still there when a repair ran. The program's process group is now stopped at the end of every run, and the run is not over until what it started is gone. A process the program deliberately detaches is still left alone.
- **A run ends when its program does.** A process the program had detached, but which still held the program's output open, kept the run from ever ending — timeout included.
- A timeout now kills everything left in the process group after the grace period, not only the process that was started.
- A timeout longer than about 24.8 days expired at once. Timeouts are also no longer thrown off by the system clock being set while a program runs.
- A request to the bridge with a body over 50 MB is answered with 413 and the rest of the body discarded. The connection used to be cut as the answer was sent, so the sender could see a broken connection instead of the reason.

### Internal

- Everything the runtime asks of an LLM goes through one interface, `AgentBackend`: a prompt and where to work in, the agent's final text out. pi is its one implementation. No change in behaviour; it is the seam for other backends.

## 0.2.2 — 2026-11-11

### Fixed

- **A repair no longer puts an unproven fix into the project.** Since 0.2.0 a proposed fix was written into the real project and run there, to be rolled back if it failed. That left the fix installed, with whatever state it had written, if the runner was stopped mid-way, and the rollback itself could fail and lose the only copy of the original. A fix is now tried on a private copy of the project; only a fix that works is installed, together with what its run produced. A fix that fails, or a runner that is stopped, leaves the project untouched because it was never written to. It still runs once.
- **Stopping the runner stops what it started.** Ctrl-C on `trama run`, or a timeout, used to leave the program and its shell commands running. A program that used a session left its participants running when it ended, timed out or yielded — and a repair could then start duplicates beside them. They are now stopped, and temporary files (including the one holding the bridge secret) are removed.
- **A single call can last longer than five minutes.** `agent.instruct()`, `tools.shell()` and `workspace.observe()` failed after 300 seconds whatever the run's timeout was.
- Shell commands run by a session participant could read the bridge secret of the program that spawned it. They no longer inherit it.
- `trama update` no longer copies the whole project aside and swaps it back on failure. The new program is validated off to the side and the project is written only once it works.
- A repair that returns an empty program, or the same program, is reported as such instead of being run again.
- The error text sent to the repair model and written to history is limited to the last part of the program's output, instead of up to 20 MB of it.
- Symlinks inside a project or workspace keep their targets when it is copied for a trial run.

### Changed

- `Session.spawn()` no longer throws synchronously for a missing project directory; like any other project that cannot be run, the failure arrives from `wait()`.
- Merging a successful repair's workspace writes now also applies deletions.

### Internal

- The release workflow is split in two: one job installs, builds, packs and tests with no publishing rights; the other only hands the packed tarballs to npm. Actions are pinned to commit SHAs, dependency install scripts are not run, and npm is no longer installed at release time — the publish job uses the npm that ships with Node 24. A release that fails part-way can be re-run.
- `tsx` and `commander` are pinned to exact versions, as pi already was.

## 0.2.0 — 2026-11-11

### Breaking

- **Node.js 22.19 or newer is required** (was 20). The upgrade to pi 1.x and commander 15 sets the floor.
- **`agent.ask()` is removed.** It was a deprecated alias; use `agent.instruct()`. A program that still calls it crashes on its next run and goes through repair.
- **`session.workspace` is now the workspace itself**, not its path. It has the same `read` / `write` / `list` / `observe` that participants get from `@trama-dev/runtime`. The path is `session.workspaceDir`.
- **`ctx.done()` and `ctx.yield()` follow one rule:** the first to succeed wins, and a call that fails settles nothing. A failed `done()` used to block `yield()` for the rest of the run.
- **`workspace.observe()` returns multiple matches in plain code-unit order**, the same as `workspace.list()`. It used to sort by locale, which differs between machines.
- **The default model is `claude-opus-5-5`** (was `claude-opus-4-6`). Projects keep the model they were created with.
- pi moved to the `@earendil-works` scope and to 1.x. Project-level pi settings (`.pi/` inside a project) are no longer loaded unless the project is trusted in pi; user-level settings in `~/.pi/agent` are unaffected.

### Security

- **The IPC bridge now authenticates its caller.** The runner listens on a loopback port, and until now any local process that found the port could have it run shell commands while a program was running. Every request must now carry a secret generated for that run and handed only to the program.

### Changed

- **A repair runs the fixed program once**, not twice. (How it does so in 0.2.0 and 0.2.1 has a flaw — see the fix in 0.2.2.)
- `ctx.done()` followed by `ctx.checkpoint()` and a crash is reported as done. It used to be mistaken for a failure and sent to repair.
- `state.json` no longer contains a `__trama_done` key.
- The API reference shown to the LLM when it writes or repairs a program is generated from the real type definitions, doc comments included.
- `trama update` on a hand-written project that has never run scaffolds it first instead of failing.
- `trama create` creates the project's module links up front rather than on first run.
- A configured model that pi does not know now produces a warning naming the model pi fell back to.
- `trama --version` reports the installed version (it reported 0.1.4 in 0.1.5).

### Added

- **A program can import `@trama-dev/session`.** The CLI installs it and every project gets a link to it, so a `program.ts` run by `trama run` can create a session and coordinate participants itself.
- `Session` expands a leading `~` in `projectDir` and `workspace`.
- `createWorkspace` and the `Workspace` type are exported from `@trama-dev/runtime/runner`.

### Internal

- The runtime was consolidated: one path guard, one child-process supervisor, a route table for the IPC server, one scaffolding function. Source shrank by about 15% with no loss of tests.
- Publishing a release marks older versions as deprecated on npm.
